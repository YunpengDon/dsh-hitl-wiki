dsh-hitl 使用与实现说明

关于这份文档

dsh-hitl 插件用于给 DeepSeek Harness（下称 DSH）里的工具调用加一道人工审核：某次调用在真正执行之前停下来，把打算做的事整理成一张卡片送到浏览器，等人回答，再把回答变成 DSH 能理解的执行前决策。

这份文档写给两类读者。

第一类是插件作者，手上有一个会改文件、跑命令、调外部服务的工具，希望人工审核后再执行工具。你需要读第 1 到 5 章，第 7 章讲人的操作会变成什么结果，第 10 章是一份排查手册。第 6 章讲界面层，读不读都不影响你把工具挂上去。

第二类是想弄懂它内部结构、准备改源码的人。在第 5 章的基础上继续读第 6、8、9 章和两个附录，那里有传输层、状态机细节、以及几个容易想错的地方。

阅读前需要的基础：会写 JavaScript，知道 DSH 的插件是通过 profile 里的一行配置加载进来的（dsh plugin add 之后会多出一行），知道"工具调用"和"会话"指的是什么。其余概念（matcher、mount、exec、request、pending）都会在第一次出现的地方解释，不需要提前准备。

文档里出现的代码片段都来自插件源码，文件名标在片段上方，方便对照阅读。

1. 它解决什么问题

在 DSH 里，模型决定调用一个工具之后，这次调用会进入工具流水线，经过若干执行前策略，然后被执行。整个过程不需要人参与。

多数时候这没有问题。但有些调用一旦执行就收不回来：一条 rm -rf、一次覆盖写入、一个直接改线上配置的 MCP 工具。这类调用需要一个看过方案的人点头。

dsh-hitl 补的就是这个环节。它把自己挂在工具流水线最靠前的位置，让被保护的工具在真正执行之前停下来，把这次调用的方案送到浏览器上等人回答，再把回答翻译成执行前决策交回流水线。

用一句话概括它的职责：在工具执行之前拦一次，问一个人，把人的回答变成决策。

它不做的事也需要提前知道，这些边界决定了你该在什么场景用它：

它不做 原因
不改写工具参数 DSH 的执行前决策只有 allow / deny / cancel / ask 四种，没有"改完再执行"这一项。第 7 章讲这种情况下【修改】按钮的语义怎么落地
不提供沙箱或事务 它只决定"要不要开始"。执行中途产生的副作用，拒绝动作回滚不了（§8.3）
不判断这次调用危不危险 哪些调用需要问人，由挂载方声明（§4.2）
不替代 DSH 自带的审批 两者问的问题不一样，可以并存（§8.4）

2. 先跑起来

这一章的目标是让你在五分钟内看到第一张卡片。原理放在后面几章。

2.1 用配置挂上第一个工具

如果你只是想给现有工具加一道确认，不需要写代码。在 profile 的插件行里加一段配置：

YAML
- id: hitl
  name: 'dsh-hitl'
  config:
    protect:
      - tool: bash
        title: 执行命令前确认
        countdown: { seconds: 30, action: reject }

protect 下面每一项就是一份"挂载"，描述哪个工具要拦、拦下来之后卡片长什么样。上面这条的含义是：每次 Agent 调用 bash，弹一张标题为"执行命令前确认"的卡片，30 秒内没人回答就按拒绝处理。

装好之后刷新一次浏览器页面，然后让 Agent 调用一次 bash。执行走到这一步时，输入区会换成一张卡片，上面是这次调用的参数、标题、几个按钮和一行倒计时。点【同意】，命令执行；点【拒绝】，命令不执行，模型收到一句说明（措辞见 §5.8）。

2.2 装完要刷新一次页面

宿主启动时会把 { endpoint, token } 写进页面 HTML，挂在全局变量 globalThis.__DSH_HITL__ 上。这份数据在页面加载的那一刻注入。

已经开着的页面，即使热重载了客户端代码，globalThis.__DSH_HITL__ 仍然是上一次加载时的内容，或者根本不存在。这时浏览器半不知道往哪里连、带什么令牌，卡片自然不会出现。刷新一次，注入才会发生。

这个坑在开发时最常踩：改完插件、重启宿主、看页面没反应，先想起这一步。

2.3 确认它真的挂上了

宿主上有一个只读接口，用来回答"现在到底挂了什么"：

Shell
curl -s http://127.0.0.1:3081/dsh-hitl/status

返回内容里有四项：当前连着的浏览器数、本进程签发过的令牌数、正在生效的挂载清单、以及还没结算的请求。看到你挂的工具出现在清单里，说明挂载生效了。

清单是拿当前时刻的样例 exec 逐条跑 matcher 得来的，所以谓词型 matcher 也会出现在里面。如果清单是空的，去宿主日志里找 dsh-hitl: 前缀的警告（§4.7）。

2.4 在插件代码里挂载

如果你正在写插件，想让自己的工具带上这道确认，做法是在 apply 里挂：

JavaScript
export const name = 'my-plugin'
export const inject = ['hitl']

export function apply(ctx) {
  ctx.hitl.protect('bash', {
    title: '这条命令要执行吗？',
    countdown: { seconds: 30, action: 'reject' },
    reject: { feedback: true },
  }, ctx)
}

第三个参数 ctx 不能省。它决定这份挂载在插件卸载时会不会一起消失，原因在 §4.4。

3. 全局地图

前面两节给的是"怎么用"。接下来的四章按层展开实现细节，这一节先把整张地图铺开，方便你在后面读到任何一处时，知道它落在图上的哪个位置。

3.1 三个层次

一次"拦一下"的动作，实际由三个彼此独立的问题组成：

层次 回答的问题 主要接口 位置
挂载层 哪些工具要拦？拦下来卡片长什么样？ protect / unprotect / list 第 4 章
门禁层 这一次调用停不停？停多久？结果怎么翻译回流水线？ tools/pre-execute 钩子、pending 表、倒计时 第 5 章
呈现层 人怎么看到这张卡，怎么把回答送回来？ composer 座位、浮层、HTTP 通道 第 6 章

这三层之所以要分开看，是因为它们各自的生命周期完全不同：挂载是长期的（装一次，一直在），门禁是每次调用一份（这次问完就没了），呈现是随时变化的（页面开着还是关着、在哪个会话里）。

可以借一栋写字楼的三个位置来记：挂载层是门口的名单（谁能进、要登记什么），门禁层是闸机（这一次到底放不放行），呈现层是前台（人在这里签字）。

分层之前，先区分三个词。它们都能被描述成"这次调用"，混用之后很多行为推不出来：

  • mount（挂载）：一份"名单条目"，由 matcher 和 options 组成，长期存在，可以随时增删。
  • exec（调用）：一次具体的工具调用，带着 name、arguments、agent、callId、signal，是一次性的。
  • request（请求）：宿主为这次调用生成的一张登记单，包含标题、字段、倒计时等内容，是给浏览器看的那份数据。

一个 mount 对应多次 exec，每次 exec 生成一个 request。第 5 章讲的 pending 表，存的就是还没结算的 request。

3.2 两个半边

插件分成两半，各自跑在不同的进程里：

半边 位置 负责
宿主半 index.js 与 lib/，跑在 Node 里 判断、状态机、倒计时、决策翻译
浏览器半 client.js，跑在页面里 画卡片、接交互、把回答送回去

两半之间由 lib/protocol.js 定义的通道连接：下行用 SSE 推帧，上行用 POST 送回决定。这条通道是插件自己拉的，没有复用 DSH 现成的 RPC。

为什么不复用，是一个构建期的约束，与使用无关。想弄清缘由的读附录 B；只想知道"为什么卡片有时要刷新页面才能连上"的，§2.2 已经够了。

3.3 一次被拦下的调用

把三层和两半串起来，一次调用会走完下面这串步骤。后面各章的细节，都能对回这里某一步：

  1. 模型发起工具调用，DSH 生成一个 exec（挂载层之外，由 DSH 负责）
  2. 流水线进入 tools/pre-execute 瀑布，dsh-hitl 因为 prepend 排在最前
  3. 门禁按注册顺序倒着找，命中第一条 matcher 的挂载（§4.6）
  4. 检查 enabled、检查有没有 agent、检查有没有浏览器连着（§5.2）
  5. 任一不通过就地返回决策，不弹卡
  6. 通过后生成 request：解析字段、算计算字段、起倒计时
  7. request 记进 pending 表，同时通过 SSE 下发给所有连着这个会话的页面（§5.5、§6.3）
  8. 浏览器半收到帧，判断这份请求该落在哪个座位（§6.1）
  9. 座位拿不到时，退到帧级浮层（§6.2）
  10. 人在卡上操作：同意、拒绝、修改、或者一直不动
  11. 上行 decide 帧带回回答，宿主校验令牌、会话、请求 ID（§8.1）
  12. 回答翻译成 PreToolDecision，交回瀑布（§5.7）
  13. 瀑布继续，沙箱、guard、审批等后续策略照常执行（§8.4）
  14. 工具执行完（或没执行），结果回到模型；卡片消失

其中第 4 步是失败关闭的入口：问不到人，就不放行。第 13 步决定了"人同意"这件事的上限：它只解开了 dsh-hitl 这一道，后面的策略照样有否决权。

4. 挂载层：哪些工具要先问人

挂载层决定的是"名单"：哪个工具要拦、拦下来之后卡片长什么样。这一层的工作全部通过一个服务对象完成，挂上去之后长期有效，直到被显式撤销。

4.1 服务 API

插件往 DSH 里注册了一个名为 hitl 的服务，对外只有四个成员：

成员 签名 作用
protect (matcher, options?, owner?) => () => void 新增一份挂载，返回一个撤销函数
unprotect (matcher) => boolean 按 matcher 的描述找到对应挂载并移除
list () => MountInfo[] 列出当前所有挂载，供诊断
pending () => PendingHitlView[] 列出当前还没结算的请求

protect 是唯一需要认真对待的一个。它有三个参数：拦谁、怎么拦、以及这份挂载的撤销权记在谁账上。前两个参数分别对应下面两节，第三个参数单独放在 §4.4，因为它是这份 API 里最容易漏掉、后果又最隐蔽的一个。

4.2 matcher：五种写法

第一个参数描述"拦谁"，有五种写法：

写法 例子 命中范围
字符串 'bash' 名字完全相同的工具
字符串加通配 'mcp__*' 所有以 mcp__ 开头的工具
'*' '*' 全部工具
数组 ['bash', 'write'] 数组里任意一个命中即可
正则 /^mcp__/ 正则匹配工具名
谓词 exec => exec.arguments.path?.endsWith('.env') 函数返回真即命中

前三种都是字符串，区别只在有没有通配符，可以算作一类。

字符串和数组里的字符串都支持 * 通配，内部会转成正则。转换过程做两件事：

JavaScript
// lib/resolve.js
function globToRegExp(glob) {
  const escaped = glob.replace(/[.+?^${}()|[\]\\]/g, '\\$&')
  return new RegExp(`^${escaped.replace(/\*/g, '.*')}$`)
}

先转义正则元字符，再把 * 换回 .*，最后加首尾锚点。两步都是为了控制匹配范围：不转义时，a.b 里的 . 会被当成"任意字符"；不加锚点时，bash 会连 subash 一起命中。

谓词写法拿到的参数是整个 exec，所以能按参数内容决定要不要拦。工具名只是它能看到的东西之一：

JavaScript
ctx.hitl.protect(
  exec => exec.name === 'write' && String(exec.arguments.path).endsWith('.env'),
  { title: '这个文件是环境配置，确认要写吗？' },
  ctx,
)

这时匹配的单位从"哪个工具"变成了"哪一次调用"。同一个工具因此可以被拆成多张不同的卡：知识树项目就把"插入节点"和"搬移节点"拆开了（§4.8）。

4.3 options：挂载选项

第二个参数是一份选项对象，全部可省略。十三个键按用途分成四组：

卡片内容

键 缺省 作用
fields 由参数自动生成 卡片正文里列哪些字段（§5.3）
diff 无 用并排 diff 代替正文，{ before, after, path? }（§5.3）

行为

键 缺省 作用
countdown null（不限时） 倒计时，{ seconds, action }，action 取 approve / reject / notify（§5.6）
reject 无 拒绝时的补充选项，{ feedback: true } 允许填理由（§5.7）
modify { mode: 'revise-request' } 【修改】按钮的语义，见 §7
whenUnavailable reject 没有浏览器连着时的行为（§8.2）
enabled true 关掉之后这份挂载等于不存在，但还能通过 list() 看到

键 缺省 作用

4.4 owner：撤销权记在谁账上

先看现象。写完 ctx.hitl.protect('bash', {...}) 之后把插件禁用或卸载，bash 依然会被拦，重启宿主才恢复。

原因在 protect 内部做的事。它只做了一件：把归一化后的挂载推进 hitl 插件 apply() 里的一个局部数组。

JavaScript
mounts.push(normalized.mount)

mounts 是 hitl 插件 apply() 里的一个局部数组，只属于那个闭包，外面看不见。这次调用没有注册监听器、没有注册服务、没有登记 effect，只是往别人的闭包数组里塞了一个元素。

Cordis 卸载一个插件时，撤销的是那个插件 fiber 名下的注册。mounts.push 不在其中，因为它在 hitl 的 fiber 上。于是这次挂载与调用方的生命周期脱了钩：调用方走了，挂载还在。

不传 owner 时，唯一的解绑手段是 protect 返回的那个 disposer。而从 apply 里 return 它并不会被调用（机制见附录 A），所以插件行卸载之后，工具会一直被拦下去。

第三个参数补上的正是这一环。传入 owner 之后，hitl 会在 owner 的上下文上登记一个 effect，把 release 挂到它的账上：

JavaScript
// index.js
if (owner !== undefined && owner !== null && typeof owner.effect === 'function') {
  try {
    owner.effect(() => release, `dsh-hitl: mount ${normalized.mount.describe}`)
  } catch (error) {
    warn(`failed to bind mount lifetime: ${String(error)}`)
  }
}

两种写法的差别：

写法 挂载登记在 卸载调用方时
不传 owner hitl 的 mounts 数组 挂载继续生效，工具一直被拦
传 owner hitl 的 mounts 数组 release 执行，挂载移除

挂载本身始终记在 hitl 名下，撤销权记在调用方名下。owner 的作用就是指定后者记在谁账上。

推荐的传法是 ctx.inject 回调里的那个 ctx：

JavaScript
ctx.inject(['hitl'], injected => {
  const hitl = injected.get('hitl')
  hitl.protect('bash', { ... }, injected)     // ← owner 用 injected，不是 ctx
})

ctx.inject(deps, cb) 会创建一个子 fiber（内部就是 this.plugin({ inject, apply: callback })），而子 fiber 的 dispose 本身又是父 fiber 上的一个 effect。父插件卸载时，子 fiber 先卸载，挂在它名下的 release 先执行。这样多出一种情况：当 hitl 服务本身消失时，依赖它的调用方会退回"等待必需服务"的状态，名下的 effect 照样跑完，挂载也能被清掉。用 ctx 当 owner 拿不到这一层保护。

万一留下了残留挂载，有两个诊断出口：

JavaScript
ctx.hitl.list()             // 看现在挂着什么
ctx.hitl.unprotect('bash')  // 按 matcher 描述清掉

想知道 owner 为什么能自动解绑、以及一种看起来等价但会静默失效的写法，见附录 A。

4.5 两个入口

挂载有两个入口，分别对应两类使用者。

入口一：profile 的配置行（不写代码）

YAML
- id: hitl
  name: 'dsh-hitl'
  config:
    protect:
      - tool: bash                      # 工具名；支持 'mcp__*' 这类通配
        title: 执行命令前确认
        countdown: { seconds: 30, action: reject }
        reject: { feedback: true }

入口二：插件的代码（写插件时）

JavaScript
ctx.hitl.protect('bash', { title: '这条命令要执行吗？' }, ctx)

两条路在 lib/resolve.js 里汇合，各自归一化成同一种 mount 对象：

TEXT
config.protect[i]   → normalizeProtectList() → mount
protect(matcher, …) → normalizeMount()       → mount

差别只有一个：配置行在插件加载时被读入，代码在 apply 里注册。谁早谁晚，决定了下一节的覆盖关系。

4.6 同一个工具只有一个门禁

同一个工具被挂载多次时，最后注册的那一份生效：

JavaScript
// lib/resolve.js
export function matchMount(mounts, execution) {
  for (let index = mounts.length - 1; index >= 0; index -= 1) {
    const mount = mounts[index]
    if (mount.test(execution)) return mount
  }
  return undefined
}

配置行先注册，插件后注册，所以插件可以覆盖配置。这个顺序带来一种实用的组织方式：配置里留一份"缺省门禁"，某个插件需要更严的规则时自己再挂一层，不用去改配置。

4.7 配置写错会怎样

normalizeMount() 会检查配置里的每一个键，但不会因为一个键写错就让整个插件加载失败：

写错的地方 结果
countdown.seconds 不是正整数 警告，退化成"不限时"
countdown.action 不在三个取值里 警告，退化成"不限时"
modify.mode 不认识 警告，退回 revise-request
matcher 完全不可用 这一条挂载作废，其余照常

所有警告统一带 dsh-hitl: 前缀落到宿主日志，例如：

TEXT
dsh-hitl: config.protect[0]: countdown.seconds must be a positive integer number of seconds

另有一条主动警告，专门针对两个单独看都正常、凑在一起会出事的选项：

JavaScript
// lib/resolve.js
if (unavailable === 'wait' && countdown === null) {
  report('whenUnavailable: wait without a countdown blocks an unattended call until its session ends; '
    + 'pair it with countdown.seconds or use the fail-closed default')
}

whenUnavailable: 'wait' 表示没有浏览器时不拒绝，一直等；countdown: null 表示不给任何时限。一次挂起的调用本来有两个出口——有人来回答，或者倒计时到期按超时策略处理。countdown: null 拿掉了第二个；而在无人值守的场景里（headless 运行、CI、你把页面关了），第一个也是空的。于是这次调用会一直挂着，直到整个会话结束。中断这一轮或者卸载宿主当然也能结束它，但那属于意外，不算策略。

4.8 一个完整例子：知识树项目的六条挂载

dsh-knowledge-tree 用这套服务把自己的工具挂了出去。它不自己画卡片，只把工具挂到 dsh-hitl 上：

5. 门禁层：这一次调用停不停

挂载决定"要不要问"，门禁决定"怎么问、问多久、问到什么结果"。这一章从挂点开始，依次讲判断顺序、卡片内容、状态机、超时、以及结果如何翻译回 DSH。

5.1 挂在哪：tools/pre-execute 与 prepend

DSH 的工具流水线在真正执行之前会走一次瀑布流程：

TypeScript
// packages/core/tools/src/index.ts
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)

dsh-hitl 挂在这条瀑布上，并且排在最前面：

JavaScript
ctx.on('tools/pre-execute', (exec, next) => gate(exec, next), { prepend: true })

prepend: true 的含义是"先问用户"。用户同意之后，沙箱、guard、hooks、审批等其它策略照常随后生效。因此用户的同意不等于越权——这一点在 §8.4 还会展开。

5.2 三道判断

gate() 进来之后先做三次判断，任何一次不通过都不会弹卡：

TEXT
① matcher 命中了吗？这张卡现在生效吗？
   → 没命中，或 enabled 是 false：直接 next()，等于这道门没装

② 这次调用有 agent 吗？
   → 没有：拒绝（"没有人可以接收这个决定"）

③ 有浏览器连着吗？
   → 没有，且 whenUnavailable 是 reject：拒绝（fail-closed）

第三道判断的代码：

JavaScript
if (clients.size === 0 && mount.options.whenUnavailable === 'reject') {
  warn(`tool ${JSON.stringify(exec.name)} needs a human decision but no browser is connected`)
  return unavailable(exec, 'no browser is connected to decide')
}

这时模型收到的是：

TEXT
Error: HITL: no browser is connected to decide, so tool "x" did not run (fail-closed).

如果希望无人值守时一直等，需要显式选 whenUnavailable: 'wait'，这相当于选择了 fail-open 的策略，所以挂载时宿主会给警告（§4.7）。

5.3 卡片上写什么：默认、diff、逐字段

卡片正文由 options 里的两个键决定：fields 和 diff。按从简到繁的顺序讲，先用默认，再讲只想看 diff 的简化写法，最后讲逐字段控制。

什么都不配时的默认行为

不写 fields 时，宿主为每个参数生成一个字段：

JavaScript
// lib/fields.js
export function defaultFieldSpecs(execution) {
  // 尝试获取合法参数对象
  const args = argumentsOf(execution)
  // 如果拿不到合法参数对象，返回兜底字段
  if (args === undefined) return [{ param: '(arguments)', render: 'json' }]
  // 如果参数对象是空对象，返回兜底字段
  const keys = Object.keys(args)
  if (keys.length === 0) return [{ param: '(arguments)', render: 'json' }]
  // 如果有具体参数，就为每个参数名生成一个字段
  return keys.map(param => ({ param }))
}

当前版本默认渲染成 markdown 输入框：

JavaScript
export function inferRender() {
  return 'markdown'
}

非字符串值先序列化成缩进 JSON：

JavaScript
export function renderValue(value) {
  // 把任意值转换成一个用于展示的字符串：
  // 字符串原样返回，undefined 显示为 (undefined)
  // 其他值尽量用格式化 JSON 展示，失败则退化为 String(value)
  if (typeof value === 'string') return value
  if (value === undefined) return '(undefined)'
  try {
    const json = JSON.stringify(value, null, 2)
    return json === undefined ? String(value) : json
  } catch {
    return String(value)
  }
}

这条默认规则保证零配置也能渲染出一张待审核的卡片。多数工具用默认就够了：参数原样列出来，人看一眼就能判断。

只想看 diff：挂载级 diff

编辑类工具是个例外。edit 的参数是 old_string 和 new_string，两段文本竖着排下来，人得自己在脑子里比对。这种调用需要并排 diff。

如果 before / after 就是这次调用的全部参数，可以省掉逐个字段的声明：

JavaScript
ctx.hitl.protect('replace_text', {
  title: '替换文本',
  diff: { before: 'old_text', after: 'new_text' },
})

不配 fields 时，宿主做两件事：把 before / after 指到的两个参数从默认字段里摘掉，然后在最后追加一个只读 diff 字段（标题缺省叫 diff，可用 diff.title 改）。上面这张卡因此只有一个字段：old_text → new_text 的并排对照。

diff 的三个键分别对应卡上的三块内容：

键 必填 填什么 出现在卡上的哪里
before 是 参数名 左列：改动前的文本
after 是 参数名 右列：改动后的文本
path 否 参数名 左上角"变更 xxx"，提示用户这次改的是哪个文件；不写就显示"变更内容"

框的左上角那行小字长这样：

TEXT
变更 /tmp/dsh-hitl-notes.md · +2 −1

前半句由 path 决定，后面的 +2 −1 由两段文本自己算出来。

三个键填的都是参数名，因为 diff 要展示的内容来自这次调用的参数。宿主拿到名字，去参数对象里取值：

JavaScript
// lib/fields.js · diffSpec
path: typeof requested.path === 'string' ? renderValue(args[requested.path]) : undefined,
oldText: renderValue(args[before]),
newText: renderValue(args[after]),

path 的分工和另外两个不同：它存在是因为用户得知道自己正在看哪一个文件，所以一般填工具参数里的路径参数，比如 edit 的 file_path。点【修改】时模型收到的回执里没有它（§7）。

有些工具的路径由代码约定，不由参数传。比如一个只在固定配置文件里做替换的工具，参数只有旧值和新值，改的是哪个文件在代码里写死。这种卡可以不写 path，标签显示"变更内容"。

名字在参数对象里找不到时，就当作没取到：

TEXT
before / after 找不到 → 两列显示 (undefined)
path 找不到           → 标签显示"变更 (undefined)"

before / after 取不到通常是配置写错了。另一种情况是这个工具本来就没有旧文本：write 只在新建或覆盖时给出内容。硬配 diff 只会得到左边一片 (undefined)，这种卡更适合直接把 content 当正文展示，也就是什么都不配，走默认规则。

0.2.1 有一个行为要留意：默认字段在推断 render 时也会看见这个挂载级 diff，于是 before / after 之外的参数不会消失，而是各自变成同一个 diff。

JavaScript
// edit 还有 file_path；配挂载级 diff 会得到两张一样的 diff
ctx.hitl.protect('edit', { diff: { path: 'file_path', before: 'old_string', after: 'new_string' } })
TEXT
file_path             → 这个 diff
old_string→new_string → 这个 diff（追加的那个）

同理，配了 fields 时挂载级 diff 不再追加字段，而是落到每个没写自己的 diff、也没写 render 的字段上。

卡片上不止一对旧 / 新文本时，把 diff 写在字段上，别写在挂载级。

逐字段控制：fields 与 FieldSpec

fields 是一个数组，数组里可以只写参数名，也可以写完整的字段声明：

JavaScript
{ param: 'content', title: '新内容', description: '会写入文件的内容',
  render: 'markdown',        // markdown | text | diff | json | hidden
  editable: true,            // 覆盖默认可编辑性
  labels: ['不可撤销'],       // 字段级标签
  value: '固定文案',          // 该字段的文本：字面量，或 (exec) => string | Promise<string>
  diff: { before: 'old_string', after: 'new_string', path: 'file_path' } }

'file_path' 就是 { param: 'file_path' } 的简写。

这八个键回答三个不同的问题，另外两个只改外观：

TEXT
① 正文写什么？     args[param] / value / diff
② 字段叫什么？     param（必填）
③ 正文怎么显示？   render（控件形态）→ 再决定默认可编辑性

title / description / labels 只改标题和说明的样子，不参与上面三件事

完整对照：

键 缺省 管什么
param 必填 字段的身份：args[param] 是缺省正文，缺省标题也用它
title schema[param].title → param 标题行
description schema[param].description 标题下的一行说明
labels [] 标题行尾的小标签（和面板级 labels 是两回事）
value 无 直接给正文：字面量，或 (exec) => … 的计算函数（§5.4）
diff 无 把正文换成并排只读 diff，before / after / path 平时填参数名，也可以填函数（§5.4）
render 见下面的取值顺序 控件形态：markdown / text / diff / json / hidden
editable 见下面的表格 能不能在卡上改，diff / hidden 会被强制只读

正文从哪来。 只写 param 时正文是 args[param]，非字符串值先格式化成缩进 JSON。加了 value 就用字面量或函数返回值。加了 diff 就用 before → after 两侧文本，默认并排只读。

value 和 diff 通常只写一个：两个都写时 diff 优先，value 被忽略；两个都不写时，正文是 args[param]。

有一个例外：显式写 render 且不是 diff 时，上面这条不适用。比如 render: 'text' 配一个两侧都是参数名的 diff，diff 会被丢掉，正文退回 value / args[param]。原因在下面的取值顺序。

param 不一定是参数名。 缺省正文来自 args[param]，容易让人以为 param 是"从哪个参数取文本"。param 是字段的名字，不承担取值的职责：

JavaScript
{ param: 'note', value: '会覆盖同名文件' }   // note 不是 write 的参数

正文一旦由 value 或 diff 提供，args[param] 就完全不参与这张卡。param 仍然必填，因为字段需要一个稳定的名字来做四件事：

  • 身份：浏览器按它给字段做键，不能和别的字段重名
  • 标题：没写 title 时，标题就是 param
  • schema：如果它恰好是参数名，title / description 从 schema 里取
  • 回执：点【修改】时，模型看到的是 - param: 新文本（§7）

render 决定控件形态和可编辑性。

render 显示内容 默认可编辑 写 editable: false 之后
markdown markdown 预览 / 编辑 / 并排 是 仅有预览 / 并排
text 文本框 是 只读文本块
diff 并排 diff，行号对齐 否（强制） 没有变化
json 格式化 JSON 检查器 否 没有变化
hidden 不渲染。此时即使写了 value 或 diff，字段也不进面板，正文被清空 否（强制） 没有变化

render 的最终取值按这个顺序定：

TEXT
① diff 里有函数（宿主已解析）  → diff，显式写的 render 也会被盖掉
② 写了 render                  → 按 render
③ 没写 render，但 diff 全部由参数名组成、能配出来 → diff
④ 都没有                       → markdown

① 是唯一的反向覆盖：diff 里的函数会无视你写的 render。② 用的是你写的值。③④ 是没写 render 时的回退。

JavaScript
// 规则 ② 先于 ③，diff 被丢掉，字段显示 args[param]
{ render: 'text', diff: { before: 'a', after: 'b' } }

这些规则都是兜底用的。想让人看 diff，直接显式写 render: 'diff' 最稳。

editable 有几条性质：

  • diff / hidden 由宿主强制只读，写 editable: true 也没用
  • json 的检查器本身不接受输入，标 true 只会让字段头误标成"可编辑"
  • 只读字段没有输入控件，它们的文本不会进入"修改"回执（§7）

参数之外的固定文案 { param: 'note', value: '会覆盖同名文件', render: 'text', editable: false }
参数之外的计算文案 { param: 'preview', value: exec => …, render: 'text', editable: false }（§5.4）
留在声明里但不上屏 { param: 'secret', render: 'hidden' }

边界行为

  1. fields 是白名单，没列出来的参数不会出现在面板里。写 fields: [] 不会退回默认规则，结果是只剩一个 (arguments) 字段（值是 {}）。
  2. 一条声明写错（param 为空、render 不认识、value 不是字符串或函数）→ 整条被丢掉并告警（§4.7）。
  3. diff 写坏（缺 before / after）→ 只丢 diff，字段退化成 args[param]。
  4. 字段全被丢光时，同样只剩那个 (arguments) 字段。
  5. value 的正文上限是 maxFieldChars（20000 字符），diff 每侧上限 maxDiffLines（2000 行）。
  6. 超出的字段标题旁标"内容已截断"，diff 则在文本里标"… [已截断，另有 N 行未显示]"。

5.4 计算字段：把参数之外的东西放进卡里

上面所有写法都有一个前提：要展示的文本得是这次调用的参数。实际使用中经常不满足。

§4.8 里那个 update_index 工具只接受新的索引正文，但人真正想看的是"索引文件现在是什么样、这次会变成什么样"。旧文本在磁盘上，新文本要从参数推出来，两者都不在参数对象里。

0.2.0 加入的计算字段专门应付这类卡片：value / diff.before / diff.after / diff.path 这四个位置，除了写参数名，也可以写函数（可以是 async）。宿主在弹卡前用这次调用的 exec 把函数跑一遍，返回值当正文：

JavaScript
ctx.hitl.protect('update_index', {
  title: '更新知识树索引',
  fields: [
    { param: 'content', title: '新索引正文', render: 'markdown' },
    { param: 'index', title: '索引文件的变化', render: 'diff', editable: false,
      // before 读磁盘上的旧索引，after 由新正文推出来——两者都不在参数里
      diff: { path: 'index.md',
              before: async exec => readIndexFile(exec),
              after: exec => `# 知识树索引\n\n${exec.arguments.content}` } },
  ],
})

宿主在弹卡之前把这些函数跑一遍：

TEXT
resolveFields(exec, mount)
  → 逐个 spec 看有没有函数
  → 有就调，结果当作文本
  → 拼进 request.fields

这张卡左右两列都来自函数，参数对象里没有对应的名字可取。§5.3 那条"三个键都是参数名"的前提在这里不成立。

path 单独处理。按 §5.3 的规则它要按参数名去查，查不到就在标签上写 (undefined)；可 update_index 要改的是约定好的 index.md，参数里从来没有这一项。宿主给 path 留了一条别的路：只要这张 diff 里有函数，名字查不到时就把字符串本身当路径用。

JavaScript
// lib/fields.js · readDiffSide
// 按参数名查：args 不存在，或者 args 里没有这个名字，carried 都是 undefined
const carried = args === undefined ? undefined : args[declared]
// 查不到、而且当前取的正是 path：把字符串本身当路径
if (carried === undefined && key === 'path') return declared
// 其余情况：字符串当参数名查 args，函数的结果当文本
return renderValue(carried)

before / after 没有这条出路，这是有意的：它们是卡片的正文，取不到就应当显眼地显示 (undefined)，让人看出配置有问题；path 负责的是那一行标签，写一个真实路径比写 (undefined) 更能帮人判断这次改动落在哪儿。

这条路只在 diff 的三个键里至少有一个是函数时才成立。三个键全是参数名的普通 diff 仍然按 §5.3 查参数，path 查不到就是"变更 (undefined)"。参数名仍然优先——参数里恰好真有同名参数时，取到的是参数值。

path 也可以直接填函数，宿主把返回值当标签；返回空字符串时，标签退回"变更内容"，和没写 path 一样。

失败怎么处理。 函数是插件作者写的代码，宿主不掌握它的行为：可能抛错，也可能迟迟不返回。每次调用都放进一场 Promise.race，一边跑函数，一边等计时器：

JavaScript
async function callResolver(resolver, execution, timeoutMs, label) {
  let timer
  try {
    return await Promise.race([
      Promise.resolve().then(() => resolver(execution)),
      new Promise((_resolve, reject) => {
        timer = setTimeout(() => { reject(new Error(`${label} timed out after ${timeoutMs}ms`)) }, timeoutMs)
        if (typeof timer?.unref === 'function') timer.unref()
      }),
    ])
  } finally {
    clearTimeout(timer)
  }
}

timer.unref() 那一行是为了不让一个还没到点的解析超时定时器把整个进程撑着不退出。

默认上限是 resolveTimeoutMs: 5000，慢一点就继续等，超时就当这次没算出来。超时和抛错落进同一处 catch：

JavaScript
// lib/fields.js
} catch (error) {
  const message = error instanceof Error ? error.message : String(error)
  settings.warn(`a computed field could not be resolved (${message}); the panel shows the failure instead`)
  // Degrade to a visible field, never to a blocked gate: the human can still
  // decide on the call itself, and every other field still renders.
  return { kind: 'error', message: `⚠️ 无法解析该字段：${message}` }
}

人在卡上看到的是一行提示，工具这次调用不会因此被拒绝，其它字段照常渲染：

更坏的情况是整段解析过程坏掉，连字段都拼不出来。那时提案退回"参数原样"：

整段解析坏掉时，卡照常弹出，正文退回参数原样，等人决定。

5.5 pending 状态机：恰好一次的结算

宿主给每一次被拦下的调用建一条记录，放进一个 Map：

JavaScript
// lib/pending.js
const entries = new Map()

const entry = {
  id,
  request,               // 递给浏览器的那张登记单
  countdownMs,           // 倒计时总时长；null = 不限时
  countdownAction,       // 归零后怎么判：approve / reject / notify
  remainingMs,           // 当前剩余
  startedAt: now(),      // 本次倒计时的起点
  held: false,           // 有没有被"交互中"冻结
  timer: undefined,      // 倒计时定时器
  graceTimer: undefined, // 冻结上限的定时器
  settled: false,        // 是否已经结算过
  ...
}
entries.set(id, entry)

这条记录装着一次通行的全部状态：谁在等、等到什么时候、有没有被暂停、结算过没有。围绕它有一组操作：

JavaScript
// lib/pending.js
open({ id, request, countdown, onTimeout })
settle(id, decision)   // 人做的决定
hold(id, held)         // 冻结 / 恢复倒计时
abort(id, source)      // 撤回（中断、卸载、宿主取消）
drain(source)          // 全部撤回

id 由 callId 派生：

JavaScript
const id = `hitl:${String(exec.callId ?? randomUUID())}`

用 callId 而不是新随机数，是因为一次调用的身份本来就是它的 callId。同一个 callId 重复 open 会被拒绝，返回 already-settled。

结算函数 close() 要做四件事：

TEXT
① 先清掉所有定时器
② 标记 settled，从 entries 里删除
③ 把 id 记进 settledIds
④ 调 onSettle（广播 settled 帧 + resolve 那个 Promise）

settledIds 用来区分两种"打不开"：

JavaScript
function missing(id) {
  return settledIds.has(id) ? ERROR_CODES.alreadySettled : ERROR_CODES.unknownRequest
}
TEXT
这个 id 已经结算过了 → already-settled（409）
这个 id 从来不存在   → unknown-request（404）

多窗口场景靠这个区分正常工作：先决策者生效，其他标签页收到 settled 帧后自动收起面板；如果某个标签页手慢了，它收到的是一条明确的 already-settled，而不是一句含糊的失败。

settledIds 有上限，而且不做逐条老化，直接整体清空：

JavaScript
if (settledIds.size > SETTLED_MEMORY) settledIds.clear()   // SETTLED_MEMORY = 4096

它的定位是诊断而不是账本：作用是"让迟到的决定得到一句准确的回答"，不需要永久记住每一次决定。

5.6 倒计时与持握

countdown 决定这次通行有没有时限：

JavaScript
countdown: { seconds: 30, action: 'reject', freezeOnInteract: true }

action 决定归零之后宿主怎么判：

action 工具是否执行 Agent 看到
approve 执行 无额外消息（工具正常返回）
reject 不执行 Error: HITL: no human decision arrived within Ns, so tool "x" did not run (timeout policy: reject).
notify 不执行 Error: HITL: no human decision arrived within Ns, so tool "x" did not run. Tell the user this call timed out and wait for an explicit instruction before running it.

notify 和 reject 在工具层面完全一样，都不执行，差别在给模型的那句话：reject 说"按超时策略拒绝了"，notify 说"超时了，去告诉用户，等他明确指示再重试"。

这背后是一条原则：超时不是用户做的决定，所以给模型的话必须说清楚"这不是人不同意"。

同一条原则也体现在界面上。超时的那一刻，面板不会凭空消失：

TEXT
归零 → 面板停约 5 秒（LINGER_MS）
     倒计时 chip 转成「已超时，等待宿主处理」
     按钮与输入框置灰
     底部写「已按超时策略处理」
然后才收起

客户端为此把"结算"拆成两步：

JavaScript
if (LINGER_OUTCOMES.includes(outcome)) {   // LINGER_OUTCOMES = ['timeout']
  store.finish(frame.id, outcome)          // 标记关闭，但留在屏幕上
  scheduleLinger(frame.id)                 // 5 秒后再 remove
  return
}
store.settle(frame.id, outcome)            // 用户自己点的那三个按钮：立刻收起

用户自己按的立刻收起；不是他按的，留几秒让他看清发生了什么。

提交之后的 8 秒兜底

人点了按钮，POST 成功了，但宿主那条 settled 帧理论上可能到不了——连接正好断在这一刻：

JavaScript

  .then(() => {
    setSettled(true)
    setTimeout(() => {
      if (!store.request(request.id)) return
      store.settle(request.id, 'user')       // SETTLE_GRACE_MS = 8000

提交成功后先显示「已提交」，8 秒内没等到宿主的 settled 帧就自己收起。否则一张已经决定过的卡片会一直留在输入区，而那个请求在宿主那边早就没有了。

持握：人正在填表时别催

用户一旦聚焦或编辑任何输入框，客户端会请求宿主暂停倒计时：

JavaScript
hold(id, held) {
  const entry = entries.get(id)
  if (entry === undefined) return { ok: false, code: missing(id) }
  if (entry.settled) return { ok: false, code: ERROR_CODES.alreadySettled }
  if (entry.countdownMs === null) return { ok: true, held: false }
  if (!entry.freezeOnInteract) return { ok: true, held: false }
  if (held) {
    if (entry.held) return { ok: true, held: true, expiresAt: entry.holdExpiresAt }
    entry.remainingMs = Math.max(0, entry.startedAt + entry.countdownMs - now())
    entry.held = true
    ...
    entry.holdExpiresAt = now() + holdGraceMs
    entry.graceTimer = setTimer(() => {
      entry.graceTimer = undefined
      releaseHold(entry)
    }, holdGraceMs)
    return { ok: true, held: true, expiresAt: entry.holdExpiresAt }
  }
  releaseHold(entry)
  return { ok: true, held: false }
}

这里有三处容易忽略。

暂停有上限，holdGraceMs 默认 5 分钟（300000ms），防止"关掉页面"把工具永久卡住。

恢复时重新起算基准：

JavaScript
entry.startedAt = now() + entry.remainingMs - entry.countdownMs

这一行看着绕，它保证两件事：冻结期间剩多少，恢复之后就还跑多少；下一次再冻结时，是从"恢复后的时钟"算剩余，而不是从那个已经过期的原定时刻。

倒计时用可清理的定时器实现，不用 Promise 的 race：

JavaScript
function armCountdown(entry) {
  if (entry.countdownMs === null || entry.settled) return
  const delay = Math.max(0, entry.remainingMs)
  entry.timer = setTimer(() => {
    entry.timer = undefined
    close(entry.id, OUTCOMES.timeout, timeoutDecision(entry.countdownAction))
  }, delay)
}

原因是插件被卸载时，所有这些定时器都要能被清掉。时钟是注入的（now / setTimer / clearTimer 都是参数），所以测试可以驱动秒数而不真的等，而且每一次定时器都经过同一个地方，卸载时清得干净。

JavaScript
// index.js
function toPreToolDecision(exec, request, mount, settlement) {
  if (settlement.decision.kind === 'approve') return { kind: 'allow' }
  if (settlement.decision.kind === 'cancel') return { kind: 'cancel' }
  const revising = isRevision(settlement.decision)
  if (revising && mount.options.modify.mode === 'allow-and-inform' && settlement.source === OUTCOMES.user) {
    revisions.set(exec, { request, decision: settlement.decision })
    return { kind: 'allow' }
  }
  const info = settlement.source === OUTCOMES.timeout
    ? FAILURES.timeout
    : (revising ? FAILURES.revised : FAILURES.rejected)
  return {
    kind: 'deny',
    reason: capReason(describeDecision(request, settlement.decision, settlement.source)),
    info,
  }
}

cancel 与 deny 的区别在于：deny 是一条"策略拒绝"的工具结果，带 reason 和 info；cancel 是 DSH 的规范取消结果，表示同一次 turn 被中断。撤回不是拒绝，它不该在模型眼里看起来像"有人不同意"。

6.2 够不着时的兜底：帧级浮层

所以 dsh-hitl 另外注册了一个 root 作用域的浮层：

"够不着"不靠猜会话状态，而是面板自己每秒做一次命中测试：

JavaScript
const OBSCURE_POLL_MS = 1000

export function isObscured(element) {
  ...
  const rect = element.getBoundingClientRect()
  if (rect.width <= 0 || rect.height <= 0) return true
  const x = rect.left + rect.width / 2
  const y = rect.top + Math.min(rect.height / 2, OBSCURE_SAMPLE_INSET_PX)
  if (x < 0 || y < 0 || x > window.innerWidth || y > window.innerHeight) return true
  const top = doc.elementFromPoint(x, y)
  return top === null || top === undefined || !element.contains(top)
}

这段代码回答的是座位真正关心的问题：这个请求能不能在它被画出来的地方被决定。一个盖住它的模态遮罩、一个被裁剪的祖先、一个被滚出视口的卡片，给出的都是同一个答案，而这三种情况在布局数字里都看不出来。

结果就是面板一旦真的在眼前，浮层立刻让位，不会双份显示。

6.4 子代理穿透：一份请求，两份归属

同进程子代理（spawn / fork）里的每一次工具调用都走同一道门禁，因为工具流水线是同一条。

这里立刻出现一个问题：那次调用发生在子会话里，而待决策值按会话归属——只有你正在看的那个会话有请求，面板才会接管它的输入区。你在看主会话，子代理的请求就落不到任何面板上。

插件给每个请求做两份归属：

归属 作用
发起调用的会话 你点进那个子代理会话时，面板就在那里
你当前正在看的会话 无论你在看哪个会话，面板都出现在你眼前的输入区

代码上是一份请求加一个视图副本：

JavaScript

  const own = request?.sessionId
  if (typeof own !== 'string' || own === '') return []
  if (typeof viewSessionId !== 'string' || viewSessionId === '' || viewSessionId === own) return [own]
  return [own, viewSessionId]
}

副本不是第二个主人，它把决定转交给原请求：

JavaScript

  constructor(primary, sessionId) {
    this.kind = KIND
    this.key = `${primary.key}@view`
    this.sessionId = sessionId

  get sequence() { return this.primary.sequence }

两份归属指向同一个请求，在哪一处决策都结算同一次调用，先答的先算。你切换会话时，这份"跟随"归属会自动迁移，因为客户端订阅了"当前显示的会话"这个绑定源：

必须做这件事的原因写在注释里：DSH 侧栏那一行的状态点只认内置的 approval / plan-review / question 三种种类，本插件的 kind: 'hitl' 不在其中，所以子会话那一行不会有任何红点。没有"跟随"归属时，一个子代理的挂载调用会静默等到倒计时结束。

会触发吗？ 取决于子代理的后端：

子代理后端 是否触发 说明
spawn / fork（同进程） 会 子代理就是同进程里的另一个 agent，工具流水线是同一条
dsh-sdk / acp / claude-code / codex（跨进程） 不会 它们的工具调用在另一个进程里发生，不经过 tools/pre-execute

触发之后，子代理那一次调用停在门禁上（它的 turn 卡住），父代理的 subagent 调用在等子代理，于是整轮对话一起停。你在界面上看到的可能只是"子代理还在跑"。

由此带出一条实务建议：给可能被子代理调用的挂载配 countdown。没有倒计时就是无限等，而子代理那边没有人会替你点。

6.5 倒计时永远是宿主的数字

倒计时有一个很容易踩的失败模式。一张卡片的 request 对象只在弹卡时构建一次，它带的 remainingMs 是倒计时的全长，而不是"现在还剩下多少"。而这个对象会被反复送出去：

TEXT
新请求的 request 帧
重连时的 snapshot 帧
hold 的 ack 帧

如果每次都原样重发，一个过一会儿才收到它的浏览器（刷新页面、断线重连、客户端半热重载）会把已经跑掉的那段时间又加回来，面板就会"声称"一段这次调用已经没有的时间。

所以每一帧都不能带那个原始对象，而要带宿主当下算出的剩余量。宿主的做法是一个投影函数：

JavaScript
function liveRequest(request) {
  if (request.countdown === null || request.countdown === undefined) return request
  const remainingMs = registry.remaining(request.id)
  if (remainingMs === null) return request
  return { ...request, countdown: { ...request.countdown, remainingMs, held: registry.held(request.id) } }
}

它被用在上面那三个地方，每一处递出去的都是"此时此刻"。

浏览器半收到之后，把它当成一次读数来用，而不是"从现在开始重新数"：

JavaScript
export function deadlineOf(reading, now) {
  const remainingMs = reading?.countdown?.remainingMs
  if (typeof remainingMs !== 'number') return undefined
  const observedAt = typeof reading.observedAt === 'number' ? reading.observedAt : now
  return observedAt + remainingMs
}

这个读数的含义是"收到它的那一刻还剩这么多"。把它锚在到达时刻上，带来三个好处：重新挂载、重复收到帧、重渲染都不会把截止时间往后推。还有一个不显眼的好处——它只信"时长"，从不信"时间戳"，因此天然不受宿主与浏览器之间的时钟偏差影响。

前台显示的那个数字由三件输入合成：

JavaScript
export function reconcileClock({ id, at, frozen, hostHeld, now }) {
  let deadlineAt = at
  let hold = frozen
  if (hostHeld) {
    if (hold === undefined || hold.id !== id) {
      hold = { id, remainingMs: deadlineAt === undefined ? 0 : Math.max(0, deadlineAt - now) }
    }
  } else if (hold !== undefined && hold.id === id) {
    if (deadlineAt !== undefined) deadlineAt = now + hold.remainingMs
    hold = undefined
  }
  const remaining = hold !== undefined
    ? hold.remainingMs
    : (deadlineAt === undefined ? undefined : deadlineAt - now)
  return { at: deadlineAt, frozen: hold, remaining }
}

注释里写着这三条规则各自修掉过一个真实的缺陷：

TEXT
1. 暂停开始时把剩余量抓一次；暂停期间这个数不动，
   否则"已暂停"的面板还在自己往下走。

2. 恢复时，在同一处把截止时间重新起算，
   否则恢复的那一帧会画出那个已经过期的原始截止时间。

3. 没有暂停时，每次渲染都从截止时间推出剩余量——
   这正是倒计时会跳的原因。

客户端只信宿主对暂停的判定：

JavaScript
setHold(id, held) {
  if ((state.holds?.[id] === true) === held) return
  state = { ...state, holds: { ...state.holds, [id]: held } }
  emit()
}

一个本地的 focus 标志，不能声称一个宿主没有批准的暂停。刷新页面时也会从 snapshot 里读到 countdown.held，暂停状态不会因为刷新而假装还在暂停。

7. 人点了什么，Agent 收到什么

前面几章分散讲过一部分，这一章集中给出完整对照，其中有一处最容易让人意外：改了文本之后点【修改】，工具默认不会执行。

用户动作 工具是否执行 Agent 收到
【同意】 执行 工具正常结果
改了文本后【修改】（默认 revise-request） 不执行 HITL: the user revised the proposal, so tool "x" did not run. Re-issue the call with these changes: + 每个改动字段的 - param: 新文本
改了文本后【修改】（allow-and-inform） 执行 工具正常结果 + 一条紧随其后的 user 消息，内容是用户改后的文本
【拒绝】 不执行 HITL: the user rejected tool "x" and it did not run.；填了反馈栏则是 … User feedback: <原文>
倒计时 / 无决策端 / 请求被撤回 见 §5.6 与 §8.2 上表里的对应文案；撤回时返回 DSH 的规范取消结果

为什么【修改】默认不让工具执行？

原因在 DSH 那一侧：执行前不允许改写工具参数，PreToolDecision 只有 allow / deny / cancel / ask 四种，"改写参数"仍然是 proposed 状态的设计。

所以 dsh-hitl 的"修改"是把用户改后的内容交回 Agent，让 Agent 用新参数重新发起一次调用。这样语义最诚实——工具确实没有按旧参数跑；日志也自洽——会话记录里不会出现"参数是 A、执行的是 B"。

如果你的工具本来就能接受"先执行、再被告知修改"（例如只是记录 / 展示类），把 modify.mode 设为 allow-and-inform。

这一分支的实现顺手解决了一个泄漏问题：

JavaScript
// index.js

  const revision = revisions.get(exec)

8. 安全边界

这一章回答两个问题：问不到人的时候怎么办，这道门禁到底守得住什么。

8.1 通道的三道校验

决策通道只认回环地址，令牌比较用常数时间：

JavaScript
function authorized(req, queryToken) {
  const header = req.headers.authorization
  const bearer = typeof header === 'string' && header.startsWith('Bearer ') ? header.slice(7) : undefined
  const presented = typeof queryToken === 'string' && queryToken !== '' ? queryToken : bearer
  if (typeof presented !== 'string' || presented === '') return false
  const candidate = Buffer.from(presented)
  let accepted = false
  for (const known of tokens) {
    const expected = Buffer.from(known)
    // Every candidate is compared, so timing does not reveal which token matched.
    if (candidate.length === expected.length && timingSafeEqual(candidate, expected)) accepted = true
  }
  return accepted
}

循环里没有提前 break，每一个候选都要比一遍，这样"比到第几个才匹配"不会从耗时上漏出去。

POST 这一侧还多两道：

JavaScript
if (!loopback(req) || !authorized(req, url.searchParams.get('token')) || !sameOrigin(req)) { ... }
if (typeof contentType !== 'string' || !contentType.includes('application/json')) { ... }

再加上请求体上限 maxBodyBytes: 256 * 1024。

这些检查挡的是本机别的网页（CSRF / DNS rebinding），不是本机进程——本机进程本来就能读 ~/.dsh。

令牌本身还有一个设计：它在一个进程内只签一次。

JavaScript
function processTokens() {
  const existing = globalThis[TOKEN_REGISTRY]
  if (existing instanceof Set) return existing
  const registry = new Set()
  Object.defineProperty(globalThis, TOKEN_REGISTRY, { value: registry, enumerable: false })
  return registry
}

令牌被注入到每一个被服务的页面里。如果插件重载时换一个新令牌，每个开着的页面都会拿着旧令牌，它的事件流再也打不开，除非人去刷新页面。所以第一次激活时签一个，之后的每次激活都复用它，而且这个进程签发过的每一个令牌都继续被接受，直到上限把它挤出去。上限是 8（TOKEN_MEMORY），最老的先掉。

8.2 没有浏览器时：默认拒绝

whenUnavailable 决定无人值守时怎么办，默认值是 reject：没有任何浏览器连着时，挂了门禁的工具会被拒绝。

问不到人就不放行。这条默认值还有一条不随 UI 存在与否而改变的语义：插件在没有任何 Web 服务的组合里（headless / TUI）仍然激活并继续拦。"没有 UI 就不拦"不是本插件的语义。

/status 这条路由是有意保留的口子：

JavaScript
if (url.pathname === `${endpoint}/status`) {
  // Read-only troubleshooting surface: no token, no payload, loopback only.
  if (req.method !== 'GET' || !loopback(req)) { ... }
  sendJson(res, 200, {
    ok: true,
    clients: clients.size,
    tokens: tokens.size,
    protecting: service.list(),
    pending: service.pending().map(request => ({ ...request,
      remainingMs: registry.remaining(request.id), held: registry.held(request.id) })),
  })
  return
}

它只包含连接着的浏览器数、本进程签发过的令牌数、正在挂载的工具、待决策列表（工具名 / 会话 id / 剩余毫秒 / 是否暂停），不包含令牌，也不包含任何工具参数。

这个暴露面的尺度写在注释里：同机进程本来就能读 ~/.dsh/sessions/** 的会话日志，那里有完整的工具参数，所以 /status 的暴露面是它严格更小的子集。

8.3 拦得住什么、拦不住什么

门禁只装在调用开始之前这一个位置上，所以它管的是"要不要开始"，管不了"开始之后发生了什么"。

有一条限度必须接受：如果工具在自己的执行层已经产生了副作用（并发竞态、异步落盘、已经发出去的外部请求），拒绝只能阻止接下来发生的事，回滚不了已经发生的事。

因此，HITL 既不是事务，也不是沙箱。

实际安全程度取决于两件事：你的 matcher 覆盖了多危险的操作，以及工具是否把不可逆动作放在最后一刻。把 bash / write / edit 这类"入口即危险"的工具挂上是对的；若某个工具的风险要到执行中途才出现，HITL 只能替你决定"要不要开始"。

8.4 与 DSH 其它机制的关系

dsh-hitl 在这条流水线上排在最前面，但它后面还站着别人。

先问人，后安检。 本插件用 tools/pre-execute 且 prepend: true，用户同意后，沙箱、guard、hooks、审批等其它策略照常随后生效。这一点在宿主代码里能直接看到——瀑布返回 allow 之后，还有一道 guard 检查：

TypeScript
const denialReason = decision.kind === 'allow' ? this.guardReason(exec) : decision.reason

于是会出现一种看起来矛盾、实则符合设计的现象：用户同意了，工具仍被沙箱 / 守卫拒绝。反过来也成立：别的执行前策略可能在本插件之前就拒绝，此时 HITL 面板根本不会出现。所以"没弹面板就直接执行了"和"没弹面板就直接失败了"这两种现象，都要先去看别的策略。

审批问"要不要"，HITL 问"照这个方案做不做"。 DSH 自带一条审批缝（ctx.approval），和 dsh-hitl 是两件不同的事：

TypeScript
// docs/subsystems/approval.md
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'

allowed-once 只授权被问到的那一次动作；调用方在 rejected / cancelled / unavailable 上一律拒绝。它的请求故意不带参数：

TEXT
ApprovalRequest deliberately omits tool arguments:
an answerer attaches the prompt to the already-streamed tool call through callId
instead of rendering a second copy that could drift.

对比一下：

DSH 自带审批 dsh-hitl
问的问题 这个动作能不能做 这一次调用照这个方案做行不行
给什么看 一个提示，挂在已经流出的工具调用上 标题 + 提案（参数 / diff / 计算字段）
能回答什么 允许一次 / 拒绝 同意 / 修改 / 拒绝（可带理由）
归属 会话策略 ask / never 每一个工具的挂载
失败关闭 unavailable 一律拒绝 whenUnavailable: reject

10.1 卡片没出现

按挂载层的顺序查三步。

第一步看 matcher。最省事的办法是调 ctx.hitl.list() 或看 /status 的 protecting 字段，确认挂载在不在。在的话再看 matcher 是否真能命中——通配串和正则都容易写偏，比如 mcp__* 只会匹配以 mcp__ 开头的名字。

第二步看 enabled。它是布尔值或一个 (exec) => boolean，按次判断时返回 false 就等于这次没装门禁。

第三步看日志。配置写错不会让插件加载失败，只会在日志里留一条 dsh-hitl: 开头的警告，容易被忽略。

如果这三步都正常，那么问题可能在别的执行前策略上：某个更早的钩子已经把这轮 turn 拒了，面板自然没有机会出现。

10.2 卡片出现但点同意后失败

这通常是正常的。HITL 排在流水线最前面，用户同意之后，沙箱、guard、hooks 照常生效。所以"同意"通过的是"要不要执行"这一关，后面的关仍然要过。看工具结果里的错误码，如果是 HITL_* 开头，说明是本插件拒的；如果是别的，去看对应子系统。

10.3 卸载插件后还在拦

protect() 没传 owner。挂载记在 hitl 的闭包里，调用方的 fiber 卸载不会动它。临时清掉用 ctx.hitl.unprotect('tool')，根治看 §4.4。

10.4 子代理一直卡着

现象是界面上显示"子代理还在跑"，但没有任何卡片。先确认子代理后端是不是同进程的 spawn / fork——跨进程后端不经过 tools/pre-execute，不会触发。如果确实是同进程，那么它的调用正停在门禁上等决策，而你没有在看着那个会话。解决办法是给这类挂载配 countdown，让超时策略兜底。

10.5 倒计时显示不对

先分清是"数字跳"还是"数字不减"。数字跳通常是渲染时重新起算导致的（§6.5 的第三条规则）；数字不减是暂停状态没解除，检查宿主侧 hold 的 graceTimer 是否已经触发（默认 5 分钟上限）。

附录 A：owner 背后的机制

这一节解释 §4.4 里那条规则背后的机制：owner 为什么能自动解绑，以及一种看起来等价、其实会静默失效的写法。只想会用的话，§4.4 就够了。

A.1 effect 的寿命契约

"传了 owner 就自动解绑"能成立，靠的是 Cordis 对 effect 的一条硬契约：

TEXT
`execute` runs immediately; the disposers it produces are collected and run
(in reverse order) either when the returned disposer is called or
when the fiber unloads, whichever comes first.

拆开看是三步：

TEXT
① effect 的体部代码立刻执行，它产出的 disposer 被收集起来
② 触发时机有两个：返回的 disposer 被调用，或者这个 fiber 卸载
③ 谁先到算谁

所以 owner.effect(() => release, label) 的含义是把这个 release 登记在 owner 那个 fiber 的账上。owner 的插件被卸载、禁用、重载或因配置变更重启时，fiber 卸载，名下 effect 逆序执行，release() 被执行，这个挂载从 hitl 的 mounts 数组里被 splice 出去。

A.2 为什么从 apply 返回的清理函数不会被调用

同样是"返回一个函数"，一处被收集，一处被丢掉：

写法 结果
function apply(ctx) { return release } 丢掉
ctx.effect(() => release, label) 收集

原因在于 Cordis 的"类分支"只认一套初始化协议。两条路完整贴出来：

TypeScript
// vendor/cordis/src/fiber.ts
execute: function () {
  if (isConstructor(runtime.callback)) {
    const instance = new runtime.callback(this.ctx, this.config)
    for (const hook of instance?.[symbols.initHooks] ?? []) {
      hook()
    }
    return instance?.[symbols.init]?.()                            // ← 只返回协议方法的返回值
  } else {
    return runtime.callback(this.ctx, this.config)                 // ← 返回值就是账
  }
},

isConstructor 只做一件事：

TypeScript
export function isConstructor(func: any): func is new (...args: any) => any {
  // async function or arrow function
  if (!func.prototype) return false
  if (func instanceof GeneratorFunction) return false
  ...
  return true
}
TEXT
同步 function 有 prototype      → true  → 走"类分支"
箭头函数 / async function 没有   → false → 普通调用
generator / async generator     → false → 普通调用

这里有一个非常容易想错的地方：new 并没有丢掉那个函数。new 的规则是"返回值是对象就用它，否则用新建的实例"，而函数也是对象：

JavaScript
function nothing() {}
new nothing()                  // {}          —— 没有返回值，用新建的实例

function primitive() { return 42 }
new primitive()                // {}          —— 返回原始值，也用新建的实例

function apply() { return () => {} }
typeof new apply()             // 'function'  —— 返回对象（函数也是对象），就用它

所以 instance 拿到的就是你 return 的那个 disposer。问题出在下一行：Cordis 的类分支认为 instance 是一个 Service 实例，于是去读 instance[initHooks] 和 instance[init]——那是 Service 子类用来声明"我注册了什么"的协议方法。一个普通的 disposer 函数身上没有这两样东西，于是 instance?.[symbols.init]?.() 短路成 undefined，整个 execute 返回 undefined，账本上就什么也没有。

实测账本（直接看 fiber._disposables）：

TEXT
A  function apply(ctx) { return d }     isConstructor = true
   ledger: [(effect wrapper)]                     ← d 不在里面

B  const apply = ctx => d               isConstructor = false
   ledger: [(effect wrapper), d]                  ← d 在里面

   类分支从 new apply(ctx) 拿到手的东西：
     typeof = function，tag = "returned-from-apply"   ← new 确实把它返回了
   但它读的是：
     initHooks = undefined，init = undefined           ← 所以它看不见这笔账

箭头函数那条路能成立的原因也在这里：

TEXT
new applyArrow(...)  →  TypeError: applyArrow is not a constructor

它根本不能被 new，这正是 isConstructor 返回 false 的原因，于是走普通调用，返回值被收集。

完整的写法矩阵：

apply 的写法 isConstructor 返回值进账本吗
function apply(ctx) { return d } true 不进
async function apply(ctx) { return d } false 进
function* apply(ctx) { yield d } false 进
const apply = ctx => d false 进
Service 子类 true 走 [Service.init] 协议

只有同步的 function 声明这一种写法会踩坑，而它恰恰是 DSH 插件最惯用的写法：

JavaScript
export function apply(ctx, config = {}) { ... }

Service 子类走的是另一套协议，所以不受影响：

TypeScript
// DSH 里的真实写法
async* [Service.init](): AsyncGenerator<() => Promise<void>, void, unknown> {
  ...
}

它 yield 出来的每一个 disposer 都会被收下。而 ctx.effect 走的就是收账那条路，它明确收集返回的函数：

TypeScript
// vendor/cordis/src/fiber.ts —— _execute()
const effect: Effect = runner.execute.call(this)
if (typeof effect === 'function') {
  return runner.collect(effect)      // ← 这里收
}

实测四种写法，把调用方插件逐个卸载（用本仓库里的 vendor/cordis 跑）：

TEXT
1: owner = 调用方 ctx            → 卸载 → "bash" released ✓
2: 不传 owner，从 apply return   → 卸载 → "write" STILL MOUNTED ✗
3: 调用方自己包一层 ctx.effect   → 卸载 → "edit" released ✓
4: owner = ctx.inject 的 ctx     → 卸载 → "glob" released ✓

第 2 行对应的就是 §4.4 开头那个现象：插件行被卸载后挂载仍然生效，工具依然会被一直拦截。

附录 B：为什么它自己拉一条通道

日常使用不需要读这一节。它解释的是 §3.2 里那句"插件自己开了一条 HTTP 通道"背后的约束，以及这些约束如何决定了后面几乎所有的实现细节。

B.1 两条现成通道都走不了

DSH 里宿主到浏览器本来有两条现成通道，但它们的席位都在构建期。

通道一：Remote 命名空间（Typert）。

一个包想让浏览器调用自己的宿主方法，要走一整条生成链：

TEXT
业务包里用 @Remote 标注方法、绑定一个 wire 命名空间
  → 构建期由 dsh-typert-generator 分析公开类型
  → 产出 /remote 工件（可执行 schema 工厂 + 声明）
  → 客户端 assembly 显式 import 这些工件
  → ctx.remote.$mount(contribution) 把它挂上去

每一步都发生在构建期，而不是运行期：

TEXT
生成器：Generation runs only at build time and never in a live agent session.
装配清单：The capability set is fixed by explicit build-time value imports;
         the Client does not discover the Host's active Services or
         Remote definitions at runtime.
          Additional capabilities require an explicit `/remote` value import
          and mount in this assembly.

那份"装配清单"就是已发布 shell 里的一串显式 import：

TypeScript
// packages/api/remotes/src/client/index.ts
import userQuestionsRemote from '@deepseek-ai/dsh-user-questions/remote'
import commandsRemote from '@deepseek-ai/dsh-commands/remote'
import goalsRemote from '@deepseek-ai/dsh-goal/remote'
// …每一个都是构建期就写死的一行

通道二：转发事件白名单。

宿主事件转发到浏览器，靠的是一张写死在源码里的白名单：

TypeScript
// packages/api/remotes/src/remote-events.ts
/**
 * The one home of this application's forwarded-Host-event allowlist.
 * …the legal key set of `ctx.remote.$on`.
 */
export const API_REMOTE_FORWARDED_EVENTS = [
  { event: 'agent-preset/selected', mode: 'emit' },
  { event: 'approval/request', mode: 'waterfall' },
  …
  { event: 'user-questions/request', mode: 'waterfall' },
] as const satisfies readonly TypertForwardableEventEntry[]

这份声明同时是三样东西：宿主侧的转发循环、客户端的合法事件键集合（$on<Event extends TypertRemoteEvent>）、以及 TypeScript 的类型面。缺了它在编译面里 TypertRemoteEvent 就是 never，于是每一次 $on 调用都编不过。

白名单里已经有 DSH 自带的两套 HITL 面板：

TEXT
approval/request          ← DSH 自带的审批面板
user-questions/request    ← DSH 自带的提问面板

同一张桌子上坐着 approval 和 question，但没有第三把椅子。而加一把椅子的成本写在文档里：

TEXT
Forwarding one more event requires one entry in that array:
the type projection, consumer key face, and Host forwarding loop all derive from it.

B.2 一个 profile 安装的包两条都走不了

dsh plugin add 做的事是：把一个包放进 profile 的 node_modules，加一行 loader 行。

TEXT
没有仓库构建     → 没人生成 /remote 工件
没有编译这一步   → 没人往装配清单里加一行 import
没有源码         → 没人往 as const 数组里加一条

于是只剩下一条路：自己在墙上开一个孔，然后自己配锁。

严格说，限制不在物理层面，而在构建期：那个位置没有留给 dsh-hitl 的席位。客户端模块表有 external 字段，允许一个条目声明它需要的非基线模块；一个客户端插件原则上也能自己 $mount 一份预生成的 contribution。但那要求插件作者在发版时跑生成器、把工件一起发出来。

B.3 这条约束带来的连锁后果

选择自己拉线，决定了后面几乎所有实现细节：

TEXT
因为线是自己拉的 → 需要自己的令牌、自己的握手、自己的重连
因为线是自己拉的 → 需要自己判断"页面还在不在"（心跳与看门狗）
因为线是窄的     → 提案必须在宿主侧算好，前端只做渲染

第三行对应 §5.4 的计算字段：内容在宿主侧算好再推给浏览器，前端只负责渲染。浏览器半因此不需要读磁盘，也不需要访问外部服务，能拿到的信息仅限于宿主愿意给的那些。

About this document

dsh-hitl is a plugin for adding a human review step to tool calls in DeepSeek Harness (DSH). A call stops just before it runs, what it intends to do is turned into a card and sent to the browser, a person answers, and that answer becomes a pre-execution decision DSH understands.

This document is written for two kinds of readers.

The first is a plugin author who owns a tool that writes files, runs commands, or calls an external service, and who wants a human review before the tool runs. Read chapters 1 to 5. Chapter 7 explains what a person's action turns into, and chapter 10 is a troubleshooting guide. Chapter 6 covers the interface layer; you can skip it and still get your tool mounted.

1. The problem it solves

In DSH, once the model decides to call a tool, that call enters the tool pipeline, passes a number of pre-execution policies, and then runs. No human is involved.

Most of the time that is fine. But some calls cannot be taken back once they run: an rm -rf, an overwriting write, an MCP tool that edits production config directly. Those calls need someone who has looked at the plan to nod.

dsh-hitl fills that gap. It attaches itself to the front of the tool pipeline, stops a protected tool just before it runs, sends the plan for that call to the browser to wait for an answer, and translates the answer into a pre-execution decision that goes back into the pipeline.

In one sentence: stop once before the tool runs, ask one person, turn the answer into a decision.

What it does not do is worth knowing up front, because those boundaries decide when you should reach for it:

It does not Why
rewrite tool arguments A DSH pre-execution decision has exactly four forms — allow / deny / cancel / ask — and "change it, then run" is not one of them. Chapter 7 covers what the 【Modify】 button means in that situation
provide a sandbox or a transaction It only decides whether to begin. It cannot roll back a side effect produced mid-execution (§8.3)
judge whether a call is dangerous Which calls need a person is declared by the mounting side (§4.2)
replace DSH's own approval The two ask different questions and can coexist (§8.4)

2. Getting it running

The goal of this chapter is to get you to your first card within five minutes. The reasoning comes in later chapters.

2.1 Mount your first tool through configuration

If you only want to add a confirmation to an existing tool, you do not need to write code. Add a block to the plugin row in your profile:

YAML
- id: hitl
  name: 'dsh-hitl'
  config:
    protect:
      - tool: bash
        title: Confirm before running a command
        countdown: { seconds: 30, action: reject }

Each entry under protect is one mount: it says which tool to intercept, and what the card looks like once it is intercepted. The entry above means: every time the agent calls bash, show a card titled "Confirm before running a command"; if nobody answers within 30 seconds, treat it as a rejection.

After installing, refresh the browser page once, then have the agent call bash. When execution reaches that point, the composer area turns into a card showing the arguments of this call, the title, a few buttons, and a countdown. Press 【Approve】 and the command runs; press 【Reject】 and it does not, and the model receives an explanatory line (the exact wording is in §5.8).

2.2 Refresh the page once after installing

At startup the host writes { endpoint, token } into the page HTML, on the global globalThis.__DSH_HITL__. That data is injected at the moment the page loads.

For a page that is already open, globalThis.__DSH_HITL__ still holds whatever was there at the previous load — or does not exist at all — even after the client code has been hot-reloaded. The browser half then does not know where to connect or which token to carry, so of course no card appears. One refresh, and the injection happens.

This is the trap you hit most often during development: you change the plugin, restart the host, see nothing in the page, and forget this step.

2.3 Confirm it is really mounted

The host exposes a read-only endpoint that answers "what is mounted right now":

Shell
curl -s http://127.0.0.1:3081/dsh-hitl/status

The response has four parts: how many browsers are connected, how many tokens this process has issued, the list of mounts in effect, and the requests that have not settled. If your tool shows up in the list, the mount took effect.

The list is produced by running each matcher against a sample exec taken at that moment, so predicate matchers appear in it too. If the list is empty, look in the host log for warnings prefixed with dsh-hitl: (§4.7).

2.4 Mount from plugin code

If you are writing a plugin and want your own tools to carry this confirmation, mount inside apply:

JavaScript
export const name = 'my-plugin'
export const inject = ['hitl']

export function apply(ctx) {
  ctx.hitl.protect('bash', {
    title: 'Run this command?',
    countdown: { seconds: 30, action: 'reject' },
    reject: { feedback: true },
  }, ctx)
}

The third argument ctx is not optional. It decides whether this mount disappears when the plugin is unloaded; §4.4 explains why.

3. The map

The two sections above were "how to use it". The next four chapters open up the implementation layer by layer, so this section lays out the whole map first: wherever you land later, you will know which part of it you are standing in.

3.1 Three layers

One act of intercepting is really three independent questions:

Layer Question it answers Main interface Where
Mounting Which tools to intercept? What does the card look like? protect / unprotect / list Chapter 4
Gate Does this call stop? For how long? How is the result translated back? the tools/pre-execute hook, the pending table, the countdown Chapter 5
Presentation How does a person see the card, and how does the answer get back? the composer seat, the overlay, the HTTP channel Chapter 6

The reason to keep the three apart is that their lifetimes are completely different: mounting is long-lived (mount once, it stays), the gate is per call (asked once, then gone), and presentation changes at any moment (is the page open, which session are you in).

A useful mnemonic is three places in an office building: the mounting layer is the guest list at the door (who may enter, what has to be registered), the gate layer is the turnstile (does this one person get through), and the presentation layer is the front desk (where the person signs).

Before the layers, separate three words. All three can be described as "this call", and mixing them up makes a lot of behaviour impossible to derive:

  • mount: one guest-list entry, made of a matcher and options. It lives on, and can be added or removed at any time.
  • exec: one concrete tool call, carrying name, arguments, agent, callId, signal. It happens once.
  • request: the record the host produces for that call — title, fields, countdown — which is the data the browser sees.

One mount covers many execs; each exec produces one request. The pending table in chapter 5 holds the requests that have not settled.

3.2 Two halves

The plugin splits into two halves that run in different processes:

Half Where Responsible for
Host half index.js and lib/, running in Node decisions, state machine, countdown, translating decisions
Browser half client.js, running in the page drawing the card, taking interaction, sending the answer back

The two halves are joined by the channel defined in lib/protocol.js: frames go down over SSE, decisions come up over POST. The plugin runs that channel itself instead of reusing DSH's existing RPC.

Why it does not reuse it is a build-time constraint and has nothing to do with using the plugin. Appendix B explains the reason; if you only want to know "why does the card sometimes need a page refresh before it connects", §2.2 is enough.

3.3 One intercepted call

Putting the three layers and two halves together, one call walks through the steps below. Every detail in the later chapters maps back to one of them:

  1. The model issues a tool call; DSH creates an exec (outside the mounting layer, DSH's job)
  2. The pipeline enters the tools/pre-execute waterfall; dsh-hitl is first because of prepend
  3. The gate walks mounts in reverse registration order and takes the first matcher that hits (§4.6)
  4. It checks enabled, checks that there is an agent, checks that a browser is connected (§5.2)
  5. If any check fails, a decision is returned on the spot and no card appears
  6. Otherwise it builds the request: resolve fields, evaluate computed fields, start the countdown
  7. The request goes into the pending table and is pushed over SSE to every page connected to this session (§5.5, §6.3)
  8. The browser half receives the frame and decides which seat this request belongs in (§6.1)
  9. When no seat is reachable, it falls back to the frame-level notice (§6.2)
  10. The person acts on the card: approve, reject, modify, or does nothing at all
  11. A decide frame carries the answer up; the host validates the token, the session, and the request ID (§8.1)
  12. The answer is translated into a PreToolDecision and handed back to the waterfall (§5.7)
  13. The waterfall continues; the sandbox, guards, approval, and other policies run as usual (§8.4)
  14. The tool finishes (or does not), the result goes back to the model, and the card disappears

Step 4 is where fail-closed enters: if no person can be reached, the call is not let through. Step 13 sets the ceiling on what "the person agreed" means — it opened this one gate only, and every policy behind it still holds a veto.

4. The mounting layer: which tools ask first

The mounting layer decides the guest list: which tool is intercepted, and what the card looks like afterwards. All of this layer goes through one service object; once mounted it stays in effect until explicitly revoked.

4.1 The service API

The plugin registers a service named hitl with exactly four members:

Member Signature What it does
protect (matcher, options?, owner?) => () => void Add one mount; returns a disposer
unprotect (matcher) => boolean Find the mounts a matcher describes and remove them
list () => MountInfo[] List every current mount, for diagnostics
pending () => PendingHitlView[] List the requests that have not settled

protect is the only one that needs real care. It takes three arguments: whom to intercept, how, and whose account the revocation is filed under. The first two are the next two sections; the third gets a section of its own (§4.4), because it is the one most easily left out and the most quietly damaging.

4.2 matcher: five forms

The first argument says whom to intercept. It has five forms:

Form Example What it matches
string 'bash' a tool with exactly that name
string with a wildcard 'mcp__*' every tool whose name starts with mcp__
'*' '*' every tool
array ['bash', 'write'] anything in the array matches
RegExp /^mcp__/ the regular expression matches the tool name
predicate exec => exec.arguments.path?.endsWith('.env') the function returns true

The first three are all strings and differ only in whether there is a wildcard, so they count as one form.

Strings — on their own or inside an array — accept a * wildcard and are converted to a regular expression internally. The conversion does two things:

JavaScript
// lib/resolve.js
function globToRegExp(pattern) {
  const escaped = pattern.replace(/[.*+?^${}()|[\]\\]/g, character => `\\${character}`)
  return new RegExp(`^${escaped.replaceAll('\\*', '.*')}$`)
}

Escape the regular-expression metacharacters, turn * back into .*, and anchor both ends. Both steps control the match range: without escaping, the . in a.b would mean "any character"; without anchoring, bash would also match subash.

A predicate receives the whole exec, so it can decide from the arguments whether to intercept. The tool name is only one of the things it can see:

JavaScript
ctx.hitl.protect(
  exec => exec.name === 'write' && String(exec.arguments.path).endsWith('.env'),
  { title: 'This file is environment config — still write it?' },
  ctx,
)

The unit of matching has now shifted from "which tool" to "which call". That is how one tool can be split into several different cards: the knowledge-tree project splits "insert a node" from "move a node" (§4.8).

4.3 options: mount options

The second argument is an options object, every key of which may be omitted. The thirteen keys fall into four groups by purpose:

Card content

Key Default What it does
fields generated from the arguments which fields the card body lists (§5.3)
diff none replace the body with a side-by-side diff, { before, after, path? } (§5.3)

Behaviour

Key Default What it does
countdown null (no deadline) countdown, { seconds, action }, where action is approve / reject / notify (§5.6)
reject none extra options for rejection; { feedback: true } lets the person give a reason (§5.7)
modify { mode: 'revise-request' } what the 【Modify】 button means, see chapter 7
whenUnavailable reject behaviour when no browser is connected (§8.2)
enabled true once off, the mount behaves as if it did not exist, but list() still shows it

Appearance

Key Default What it does
title Confirm how <tool> runs, in the interface language the card title
layout 'stacked' field layout: stacked vertically / split side by side
labels [] small labels at the end of the title row, e.g. a risk level
buttons the three built-in labels override the button copy

Limits

Key Default What it does
maxFieldChars 20000 truncation length for one field body (§5.3)
resolveTimeoutMs 5000 resolution timeout for one computed field (§5.4)

Zero configuration is legal: protect('bash') gives you a card titled Confirm how bash runs, listing every argument, with no countdown and the default button labels.

4.4 owner: whose account the revocation is filed under

Start with the symptom. You write ctx.hitl.protect('bash', {...}), then disable or uninstall the plugin — and bash is still intercepted. Only restarting the host clears it.

The reason is what protect actually does. It does exactly one thing: push the normalized mount into a local array inside the hitl plugin's apply().

JavaScript
mounts.push(normalized.mount)

mounts is a local array inside the hitl plugin's apply(). It belongs to that closure and is invisible from outside. This call registered no listener, no service, no effect; it pushed one element into somebody else's closure array.

When Cordis unloads a plugin, it revokes the registrations filed under that plugin's fiber. mounts.push is not one of them, because it runs on hitl's fiber. So this mount is decoupled from the caller's lifetime: the caller leaves, the mount stays.

Without an owner, the only way to unbind is the disposer protect returns. And returning it from apply does not get it called (the mechanism is in appendix A), so once the plugin row is unloaded, the tool stays intercepted.

The third argument closes exactly this gap. Pass an owner and hitl registers an effect on the owner's context, filing the release under its account:

JavaScript
// index.js
if (owner !== undefined && owner !== null && typeof owner.effect === 'function') {
  try {
    owner.effect(() => release, `dsh-hitl: mount ${normalized.mount.describe}`)
  } catch (error) {
    warn(`failed to bind mount lifetime: ${String(error)}`)
  }
}

The difference between the two styles:

Style Where the mount is registered When the caller is unloaded
no owner hitl's mounts array the mount stays in effect, the tool is intercepted forever
with owner hitl's mounts array the release runs, the mount is removed

The mount itself is always recorded under hitl's name; the right to revoke it is recorded under the caller's. owner is how you say whose name that is.

The recommended argument is the ctx inside the ctx.inject callback:

JavaScript
ctx.inject(['hitl'], injected => {
  const hitl = injected.get('hitl')
  hitl.protect('bash', { ... }, injected)     // ← owner is injected, not ctx
})

ctx.inject(deps, cb) creates a child fiber (internally this.plugin({ inject, apply: callback })), and disposing that child fiber is itself an effect on the parent fiber. When the parent plugin unloads, the child fiber unloads first, so the release filed under it runs first. That buys one more case: when the hitl service itself disappears, a caller that depends on it falls back to "waiting for a required service", the effects under its name still finish, and the mount can still be cleared. Using ctx as the owner does not get you that protection.

If a stale mount does survive, there are two diagnostic exits:

JavaScript
ctx.hitl.list()             // what is mounted right now
ctx.hitl.unprotect('bash')  // remove by matcher description

For why owner can unbind automatically, and for a form that looks equivalent but silently fails, see appendix A.

4.5 Two entry points

There are two ways to mount, one for each kind of user.

Entry one: the profile's config row (no code)

YAML
- id: hitl
  name: 'dsh-hitl'
  config:
    protect:
      - tool: bash                      # tool name; 'mcp__*' style globs work too
        title: Confirm before running a command
        countdown: { seconds: 30, action: reject }
        reject: { feedback: true }

Entry two: plugin code (when you are writing a plugin)

JavaScript
ctx.hitl.protect('bash', { title: 'Run this command?' }, ctx)

The two paths meet in lib/resolve.js, each normalized into the same kind of mount object:

TEXT
config.protect[i]   → normalizeProtectList() → mount
protect(matcher, …) → normalizeMount()       → mount

Only one thing differs: the config row is read when the plugin loads, while code registers during apply. Which comes first decides the override relationship in the next section.

4.6 One tool, one gate

When the same tool is mounted several times, the most recent registration wins:

JavaScript
// lib/resolve.js
export function matchMount(mounts, execution) {
  for (let index = mounts.length - 1; index >= 0; index -= 1) {
    const mount = mounts[index]
    if (mount.test(execution)) return mount
  }
  return undefined
}

The config row registers first and plugins later, so a plugin can override the config. That order suggests a practical arrangement: leave a "default gate" in the config, and let a plugin mount a stricter rule of its own when it needs one, without touching the config.

4.7 What a bad config does

normalizeMount() checks every key in the config, but one bad key does not fail the whole plugin load:

What is wrong Result
countdown.seconds is not a positive integer warning, degrades to "no deadline"
countdown.action is not one of the three values warning, degrades to "no deadline"
modify.mode is unrecognized warning, falls back to revise-request
matcher is entirely unusable that one mount is dropped, the rest carry on

Every warning lands in the host log with a dsh-hitl: prefix, for example:

TEXT
dsh-hitl: config.protect[0]: countdown.seconds must be a positive integer number of seconds

There is also one warning raised on purpose, aimed at two options that are each fine alone and dangerous together:

JavaScript
// lib/resolve.js
if (unavailable === 'wait' && countdown === null) {
  report('whenUnavailable: wait without a countdown blocks an unattended call until its session ends; '
    + 'pair it with countdown.seconds or use the fail-closed default')
}

whenUnavailable: 'wait' means "do not reject when no browser is connected, just wait"; countdown: null means "no deadline at all". A suspended call normally has two exits — somebody answers, or the countdown expires and the timeout policy handles it. countdown: null removes the second. In an unattended setting (a headless run, CI, you closed the page) the first is empty too. The call then hangs until the whole session ends. Interrupting the turn or unloading the host does end it, but that is an accident, not a policy.

4.8 A complete example: six mounts in the knowledge-tree project

dsh-knowledge-tree mounts its own tools through this service. It does not draw cards itself; it only mounts tools onto dsh-hitl:

JavaScript
ctx.inject(['hitl'], injected => {
  const hitl = injected.get('hitl')
  if (hitl === undefined || typeof hitl.protect !== 'function') return
  const mounted = mountHitl(hitl, { readTree, config }, ctx)
  ctx.logger.info(`knowledge-tree: four tools mounted on dsh-hitl cards (${mounted.join(', ')})`)
})

On a local dev profile, /dsh-hitl/status shows six mounts:

TEXT
organize_tree                 organize the tree
predicate(isInsertNode)       organize the tree · insert a node        computed: true
predicate(isMoveNode)         organize the tree · move a node          computed: true
append_leaf                   append a leaf
update_index                  update the index                         computed: true
cleanup_organized_leaf        delete a leaf from the staging area      computed: true

The labels in the second column are the mounting project's own copy; they are translated here for readability.

Rows two and three are the same tool, split into two different cards by two predicates: inserting a node and moving a node need different things confirmed, and once split, each card shows only what it cares about.

The computed column marks cards whose proposal needs the host to compute something just before the card opens; see §5.4.

5. The gate layer: whether this call stops

Mounting decides whether to ask; the gate decides how to ask, how long to ask, and what result comes back. This chapter starts at the hook, then covers the order of checks, the card content, the state machine, timeouts, and how the result is translated back into DSH.

5.1 Where it hooks: tools/pre-execute and prepend

Before a tool really runs, the DSH tool pipeline goes through one waterfall:

TypeScript
// packages/core/tools/src/index.ts
const gate = await this.ctx.waterfall(
  carrier, 'tools/pre-execute', exec,
  () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
)

dsh-hitl hooks onto that waterfall and puts itself first:

JavaScript
ctx.on('tools/pre-execute', (exec, next) => gate(exec, next), { prepend: true })

prepend: true means "ask the user first". Once the user agrees, the sandbox, guards, hooks, approval, and other policies take effect afterwards as usual. So a user's approval is not a privilege escalation — §8.4 comes back to this.

5.2 Three checks

Once gate() is entered, three checks run first. If any of them fails, no card appears:

TEXT
① Did a matcher hit? Is this card in effect right now?
   → no hit, or enabled is false: call next() and the gate might as well not be mounted

② Does this call have an agent?
   → no: reject ("nobody can receive this decision")

③ Is a browser connected?
   → no, and whenUnavailable is reject: reject (fail-closed)

The code for the third check:

JavaScript
if (clients.size === 0 && mount.options.whenUnavailable === 'reject') {
  warn(`tool ${JSON.stringify(exec.name)} needs a human decision but no browser is connected`)
  return unavailable(exec, 'no browser is connected to decide')
}

What the model receives at that point:

TEXT
Error: HITL: no browser is connected to decide, so tool "x" did not run (fail-closed).

If you would rather wait indefinitely in an unattended run, you have to choose whenUnavailable: 'wait' explicitly. That is choosing a fail-open policy, which is why the host warns at mount time (§4.7).

5.3 What the card says: defaults, diff, per-field control

The card body is decided by two keys in options: fields and diff. They are covered from simplest to most involved — defaults first, then the shortcut for "just show me a diff", then per-field control.

The default, with nothing configured

With no fields, the host generates one field per argument:

JavaScript
// lib/fields.js
export function defaultFieldSpecs(execution) {
  // try to get a valid arguments object
  const args = argumentsOf(execution)
  // no usable arguments object: fall back to one field
  if (args === undefined) return [{ param: '(arguments)', render: 'json' }]
  // an empty arguments object: fall back to one field
  const keys = Object.keys(args)
  if (keys.length === 0) return [{ param: '(arguments)', render: 'json' }]
  // otherwise one field per argument name
  return keys.map(param => ({ param }))
}

The current version renders them as markdown inputs by default:

JavaScript
export function inferRender() {
  return 'markdown'
}

Non-string values are serialized to indented JSON first:

JavaScript
export function renderValue(value) {
  // turn any value into a string for display:
  // strings pass through, undefined shows as (undefined),
  // anything else is pretty-printed JSON, falling back to String(value)
  if (typeof value === 'string') return value
  if (value === undefined) return '(undefined)'
  try {
    const json = JSON.stringify(value, null, 2)
    return json === undefined ? String(value) : json
  } catch {
    return String(value)
  }
}

This default rule guarantees that zero configuration still renders a reviewable card. For most tools the default is enough: the arguments are listed as they are, and one look is enough to judge.

Just the diff: mount-level diff

Editing tools are the exception. edit takes old_string and new_string, and two blocks of text stacked vertically force the reader to diff them in their head. Those calls want a side-by-side diff.

If before / after are the only arguments that matter, you can skip declaring fields one by one:

JavaScript
ctx.hitl.protect('replace_text', {
  title: 'Replace text',
  diff: { before: 'old_text', after: 'new_text' },
})

With no fields, the host does two things: it removes the two arguments that before / after point at from the default fields, then appends one read-only diff field (titled diff unless you set diff.title). The card above therefore has exactly one field: the old_text → new_text comparison, side by side.

The three keys of diff map to three things on the card:

Key Required What goes in it Where it shows
before yes an argument name left column: the text before the change
after yes an argument name right column: the text after the change
path no an argument name top-left "change xxx", telling the user which file this touches; without it the label reads "changed content"

The small line at the top-left of the box looks like this:

TEXT
change /tmp/dsh-hitl-notes.md · +2 −1

The first part comes from path; the +2 −1 is computed from the two texts.

All three keys take argument names, because what the diff shows comes from this call's arguments. The host takes the names and reads the values out of the arguments object:

JavaScript
// lib/fields.js · diffSpec
path: typeof requested.path === 'string' ? renderValue(args[requested.path]) : undefined,
oldText: renderValue(args[before]),
newText: renderValue(args[after]),

path plays a different role from the other two: it exists so the user knows which file they are looking at, so it normally points at the tool's path argument, such as edit's file_path. It is not part of what the model receives when the person presses 【Modify】 (chapter 7).

Some tools have a path fixed by code instead of passed as an argument. A tool that only ever replaces text in one known config file takes just the old and new values; the file is hard-coded. Such a card can omit path, and the label reads "changed content".

When a name is not found in the arguments object, it counts as missing:

TEXT
before / after not found → both columns show (undefined)
path not found           → the label shows "change (undefined)"

A missing before / after is usually a config mistake. The other case is a tool that has no "before" text at all: write only supplies content, whether creating or overwriting. Forcing a diff there just yields a left column full of (undefined); that card is better off showing content as the body, which means configuring nothing and taking the default rule.

One behaviour to watch in 0.2.1: when inferring render, the default fields also see this mount-level diff, so arguments other than before / after do not disappear — each of them becomes the same diff.

JavaScript
// edit also has file_path; a mount-level diff yields two identical diffs
ctx.hitl.protect('edit', { diff: { path: 'file_path', before: 'old_string', after: 'new_string' } })
TEXT
file_path             → this diff
old_string→new_string → this diff (the appended one)

By the same token, when fields is present the mount-level diff no longer appends a field; it lands on every field that declares neither its own diff nor a render.

If a card needs more than one pair of old / new texts, put diff on the fields, not at mount level.

Per-field control: fields and FieldSpec

fields is an array whose entries may be a bare argument name or a full field declaration:

JavaScript
{ param: 'content', title: 'New content', description: 'Text that will be written to the file',
  render: 'markdown',        // markdown | text | diff | json | hidden
  editable: true,            // overrides the default editability
  labels: ['irreversible'],  // field-level labels
  value: 'fixed copy',       // this field's text: a literal, or (exec) => string | Promise<string>
  diff: { before: 'old_string', after: 'new_string', path: 'file_path' } }

'file_path' is shorthand for { param: 'file_path' }.

These eight keys answer three different questions; two more only change appearance:

TEXT
① What is the body?        args[param] / value / diff
② What is the field called? param (required)
③ How is the body shown?    render (control shape) → which then decides default editability

title / description / labels only change the heading and the note, they take no part in the three above

The full reference:

Key Default What it controls
param required the field's identity: args[param] is the default body, and the default title uses it too
title schema[param].title → param the heading row
description schema[param].description one line of explanation under the heading
labels [] small labels at the end of the heading row (not the panel-level labels)
value none supply the body directly: a literal, or a (exec) => … resolver (§5.4)
diff none replace the body with a read-only side-by-side diff; before / after / path normally name arguments and may also be functions (§5.4)
render see the order below control shape: markdown / text / diff / json / hidden
editable see the table below whether it can be edited on the card; diff / hidden are forced read-only

Where the body comes from. With only param, the body is args[param], and non-string values are formatted as indented JSON. Add value and the body is the literal or the function's return value. Add diff and the body is the before → after pair, side by side and read-only by default.

You normally write only one of value and diff: with both, diff wins and value is ignored; with neither, the body is args[param].

There is one exception: an explicit render that is not diff overrides that rule. render: 'text' together with a diff whose sides are both argument names drops the diff and falls back to value / args[param]. The reason is the resolution order below.

param is not necessarily an argument name. The default body comes from args[param], which makes it easy to read param as "which argument to take the text from". param is the field's name and carries no responsibility for fetching values:

JavaScript
{ param: 'note', value: 'will overwrite a file of the same name' }   // note is not a write argument

Once the body is supplied by value or diff, args[param] plays no part in this card at all. param is still required, because a field needs a stable name for four things:

  • identity: the browser keys fields by it, so it must not collide with another field
  • title: without title, the heading is param
  • schema: if it happens to be an argument name, title / description come from the schema
  • the receipt: when the person presses 【Modify】, the model sees - param: new text (chapter 7)

render decides the control shape and the editability.

render What it shows Editable by default With editable: false
markdown markdown preview / edit / side by side yes preview and side by side only
text a text box yes a read-only text block
diff side-by-side diff, aligned line numbers no (forced) unchanged
json a formatted JSON inspector no unchanged
hidden not rendered. Even with value or diff the field stays off the panel and its body is dropped no (forced) unchanged

The final value of render is decided in this order:

TEXT
① the diff holds a function (already resolved by the host) → diff, overriding an explicit render
② render was given                                        → use it
③ no render, but diff is made only of argument names and can be built → diff
④ none of the above                                       → markdown

① is the only reverse override: a function inside the diff ignores whatever render you wrote. ② uses your value. ③ and ④ are the fallbacks when render is absent.

JavaScript
// rule ② comes before ③, so the diff is dropped and the field shows args[param]
{ render: 'text', diff: { before: 'a', after: 'b' } }

All of these rules are safety nets. If you want a person to see a diff, writing render: 'diff' explicitly is the reliable choice.

editable has a few properties:

  • diff / hidden are forced read-only by the host; editable: true does nothing
  • the json inspector takes no input, so true only mislabels the field header as "editable"
  • read-only fields have no input control, and their text does not enter the modification receipt (chapter 7)

A demonstration card

This card uses all three display modes at once:

  title: 'Before the edit: path, diff, and renderings',
  labels: ['changes a file'],
  fields: [
    // an argument, shown as-is in a single-line box
    { param: 'file_path', title: 'Target file', render: 'text' },
    // two arguments computed into a read-only diff
    { param: 'change', title: 'What changes', render: 'diff',
      diff: { path: 'file_path', before: 'old_string', after: 'new_string' } },
    // editable markdown
    { param: 'new_string', title: 'Result after the edit', render: 'markdown' },
  ],
})

The common patterns are worth copying outright:

What you want How to write it
show an argument as-is 'file_path'
different title / a note { param: 'content', title: 'Text that will be written' }
a single-line box { param: 'file_path', render: 'text' }
a read-only text block { param: 'command', render: 'text', editable: false }

Edge behaviour

  1. fields is a whitelist: arguments you leave out never reach the panel. fields: [] does not fall back to the default rule; the result is a single (arguments) field with the value {}.
  2. One bad declaration (empty param, unknown render, value that is neither string nor function) → that entry is dropped with a warning (§4.7).
  3. A broken diff (missing before / after) → only the diff is dropped, and the field degrades to args[param].
  4. If every field is dropped, the same single (arguments) field remains.
  5. A value body is capped at maxFieldChars (20000 characters); each side of a diff is capped at maxDiffLines (2000 lines).
  6. A truncated field says "content truncated" beside its title; a truncated diff marks the text itself with "… [truncated, N more lines not shown]".

5.4 Computed fields: putting what the arguments do not carry on the card

Every form above rests on one assumption: the text to display is one of this call's arguments. In practice that often fails.

The update_index tool from §4.8 takes only the new index body, but what a person actually wants to see is "what the index file looks like now, and what it becomes after this call". The old text is on disk and the new text has to be derived from the argument; neither is in the arguments object.

Computed fields, added in 0.2.0, exist for exactly these cards: value / diff.before / diff.after / diff.path accept a function (possibly async) as well as an argument name. Before opening the card, the host runs the function with this call's exec and uses the return value as the body:

JavaScript
ctx.hitl.protect('update_index', {
  title: 'Update the knowledge-tree index',
  fields: [
    { param: 'content', title: 'New index text', render: 'markdown' },
    { param: 'index', title: 'What changes in the index file', render: 'diff', editable: false,
      // before reads the old index from disk, after derives the new text from the argument —
      // neither is one of the call's parameters
      diff: { path: 'index.md',
              before: async exec => readIndexFile(exec),
              after: exec => `# Knowledge-tree index\n\n${exec.arguments.content}` } },
  ],
})

The host runs those functions before the card opens:

TEXT
resolveFields(exec, mount)
  → walk the specs looking for functions
  → call each one, take the result as text
  → assemble into request.fields

Both columns of this card come from functions; there is no name in the arguments object to look up. The premise from §5.3 — "all three keys are argument names" — does not hold here.

path is handled separately. By the §5.3 rule it should be looked up as an argument name and labelled (undefined) when not found, but update_index changes the agreed index.md, which never appears among the arguments. The host gives path another route: as long as this diff contains a function, a name that cannot be found is used as the path itself.

JavaScript
// lib/fields.js · readDiffSide
// look up by argument name: no args, or no such name in args, leaves carried undefined
const carried = args === undefined ? undefined : args[declared]
// not found, and this is path: use the string itself as the path
if (carried === undefined && key === 'path') return declared
// otherwise: strings are looked up in args, function results are the text
return renderValue(carried)

before / after have no such escape, deliberately: they are the card's body, so a missing value should show a loud (undefined) and reveal the misconfiguration. path only fills that one label line, and a real path helps a person judge where the change lands far more than (undefined) does.

This route only exists when at least one of the three diff keys is a function. An ordinary diff made entirely of argument names still resolves them as §5.3 describes, and a missing path yields "change (undefined)". Argument names still win: if the arguments genuinely contain a parameter of that name, the parameter value is used.

path may also be a function, in which case the host uses the return value as the label; an empty string falls back to "changed content", the same as omitting path.

What happens on failure. The functions are the plugin author's code and the host does not control their behaviour: they may throw, and they may never return. Every call is put into a Promise.race between the function and a timer:

JavaScript
async function callResolver(resolver, execution, timeoutMs, label) {
  let timer
  try {
    return await Promise.race([
      Promise.resolve().then(() => resolver(execution)),
      new Promise((_resolve, reject) => {
        timer = setTimeout(() => { reject(new Error(`${label} timed out after ${timeoutMs}ms`)) }, timeoutMs)
        if (typeof timer?.unref === 'function') timer.unref()
      }),
    ])
  } finally {
    clearTimeout(timer)
  }
}

That timer.unref() line keeps a pending timeout timer from holding the whole process open.

The default cap is resolveTimeoutMs: 5000: a slow resolver keeps waiting, and a timeout counts as "not computed this time". Timeouts and throws land in the same catch:

JavaScript
// lib/fields.js
} catch (error) {
  const message = error instanceof Error ? error.message : String(error)
  settings.warn(`a computed field could not be resolved (${message}); the panel shows the failure instead`)
  // Degrade to a visible field, never to a blocked gate: the human can still
  // decide on the call itself, and every other field still renders.
  return { kind: 'error', message: `⚠️ could not resolve this field: ${message}` }
}

What the person sees on the card is one line of text; the call is not rejected for it, and the other fields render as usual:

TEXT
⚠️ could not resolve this field: diff.before timed out after 5000ms

The worse case is the whole resolution pass breaking down, to the point where no fields can be assembled at all. The proposal then falls back to "the arguments as they are":

JavaScript
// index.js
async function resolutionFor(exec, mount) {
  try {
    return await resolveFields(exec, mount, { timeoutMs: mount.options.resolveTimeoutMs, warn })
  } catch (error) {
    warn(`the computed fields of tool ${JSON.stringify(exec.name)} could not be resolved: ${String(error)}`)
    return undefined
  }
}

When the pass breaks down, the card still opens, the body falls back to the raw arguments, and the person still decides.

5.5 The pending state machine: settling exactly once

The host creates one record for each intercepted call and keeps it in a Map:

JavaScript
// lib/pending.js
const entries = new Map()

const entry = {
  id,
  request,               // the record handed to the browser
  countdownMs,           // total countdown length; null = no deadline
  countdownAction,       // how to settle at zero: approve / reject / notify
  remainingMs,           // what is left right now
  startedAt: now(),      // when this countdown started
  held: false,           // whether it is frozen by interaction
  timer: undefined,      // the countdown timer
  graceTimer: undefined, // the timer capping a hold
  settled: false,        // whether it has settled
  ...
}
entries.set(id, entry)

This record holds the entire state of one passage through the gate: who is waiting, until when, whether it is paused, whether it has settled. A small set of operations works on it:

JavaScript
// lib/pending.js
open({ id, request, countdown, onTimeout })
settle(id, decision)   // the decision a person made
hold(id, held)         // freeze / resume the countdown
abort(id, source)      // withdraw (interrupt, unload, host cancel)
drain(source)          // withdraw everything

id is derived from callId:

JavaScript
const id = `hitl:${String(exec.callId ?? randomUUID())}`

callId rather than a fresh random value, because a call's identity already is its callId. Opening the same callId twice is refused with already-settled.

The settle function close() does four things:

TEXT
① clear every timer first
② mark settled, delete from entries
③ record the id in settledIds
④ call onSettle (broadcast the settled frame + resolve that Promise)

settledIds separates the two kinds of "cannot open":

JavaScript
function missing(id) {
  return settledIds.has(id) ? ERROR_CODES.alreadySettled : ERROR_CODES.unknownRequest
}
TEXT
this id already settled → already-settled (409)
this id never existed   → unknown-request (404)

Multi-window use depends on that distinction: the first decision wins, and the other tabs drop their panel when the settled frame arrives. If one tab is slow, it gets a precise already-settled rather than a vague failure.

settledIds is bounded, and it does not age entries out one by one — it is cleared whole:

JavaScript
if (settledIds.size > SETTLED_MEMORY) settledIds.clear()   // SETTLED_MEMORY = 4096

Its purpose is diagnosis, not bookkeeping: it exists so that a late decision gets an accurate answer. It does not need to remember every decision forever.

5.6 Countdown and hold

countdown decides whether this passage has a deadline:

JavaScript
countdown: { seconds: 30, action: 'reject', freezeOnInteract: true }

action decides how the host settles at zero:

action Does the tool run? What the agent sees
approve yes no extra message (the tool returns normally)
reject no Error: HITL: no human decision arrived within Ns, so tool "x" did not run (timeout policy: reject).
notify no Error: HITL: no human decision arrived within Ns, so tool "x" did not run. Tell the user this call timed out and wait for an explicit instruction before running it.

notify and reject behave identically at the tool level — neither runs — and differ only in the sentence the model gets: reject says "rejected by the timeout policy", notify says "it timed out, go tell the user, and wait for an explicit instruction before retrying".

One principle sits behind this: a timeout is not a decision the user made, so what the model reads has to make clear that this was not a person saying no.

The same principle shows in the interface. At the moment of the timeout the panel does not vanish:

TEXT
zero reached → the panel stays for about 5s (LINGER_MS)
               the countdown chip switches to "timed out, waiting for the host"
               buttons and inputs grey out
               the footer reads "settled by the timeout policy"
then it closes

To do that, the client splits settling into two steps:

JavaScript
if (LINGER_OUTCOMES.includes(outcome)) {   // LINGER_OUTCOMES = ['timeout']
  store.finish(frame.id, outcome)          // mark closed, but keep it on screen
  scheduleLinger(frame.id)                 // remove after 5s
  return
}
store.settle(frame.id, outcome)            // the three buttons the user pressed himself: close at once

What the user pressed closes immediately; what he did not press stays a few seconds so he can see what happened.

The eight-second fallback after submitting

The person presses a button and the POST succeeds, but the host's settled frame may in theory never arrive — the connection dropping at exactly that moment:

JavaScript
pending.answer(decision)
  .then(() => {
    setSettled(true)
    setTimeout(() => {
      if (!store.request(request.id)) return
      store.settle(request.id, 'user')       // SETTLE_GRACE_MS = 8000
    }, SETTLE_GRACE_MS)
  })
  .catch(error => { setBusy(false); setFailure(error?.message ?? String(error)) })

After a successful submit the panel shows "submitted", and if no settled frame arrives within eight seconds it closes itself. Otherwise a card that has already been decided would sit in the composer forever while the request no longer exists on the host.

Hold: do not rush a person who is filling in the form

As soon as the user focuses or edits any input, the client asks the host to pause the countdown:

JavaScript
hold(id, held) {
  const entry = entries.get(id)
  if (entry === undefined) return { ok: false, code: missing(id) }
  if (entry.settled) return { ok: false, code: ERROR_CODES.alreadySettled }
  if (entry.countdownMs === null) return { ok: true, held: false }
  if (!entry.freezeOnInteract) return { ok: true, held: false }
  if (held) {
    if (entry.held) return { ok: true, held: true, expiresAt: entry.holdExpiresAt }
    entry.remainingMs = Math.max(0, entry.startedAt + entry.countdownMs - now())
    entry.held = true
    ...
    entry.holdExpiresAt = now() + holdGraceMs
    entry.graceTimer = setTimer(() => {
      entry.graceTimer = undefined
      releaseHold(entry)
    }, holdGraceMs)
    return { ok: true, held: true, expiresAt: entry.holdExpiresAt }
  }
  releaseHold(entry)
  return { ok: true, held: false }
}

Three things here are easy to miss.

A pause has a ceiling. holdGraceMs defaults to 5 minutes (300000ms), so closing the page cannot block a tool forever.

Resuming re-bases the clock:

JavaScript
entry.startedAt = now() + entry.remainingMs - entry.countdownMs

That line looks convoluted, and it guarantees two things: whatever was left when the countdown froze is exactly what runs after it resumes; and the next freeze computes the remainder from the resumed clock rather than from an original deadline that has already passed.

The countdown uses a clearable timer, not a Promise race:

JavaScript
function armCountdown(entry) {
  if (entry.countdownMs === null || entry.settled) return
  const delay = Math.max(0, entry.remainingMs)
  entry.timer = setTimer(() => {
    entry.timer = undefined
    close(entry.id, OUTCOMES.timeout, timeoutDecision(entry.countdownAction))
  }, delay)
}

The reason is that when the plugin is unloaded, all of these timers have to be cleared. The clock is injected (now / setTimer / clearTimer are all parameters), so tests can drive the seconds without actually waiting, and every timer goes through the same place, so unloading cleans up completely.

5.7 Decision → PreToolDecision

A person's answer eventually has to become something DSH understands. A DSH pre-execution decision has exactly four forms:

TypeScript
// packages/core/tools/src/index.ts
export type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string; info?: ToolErrorInfo }
  | { kind: 'cancel' }
  | { kind: 'ask'; reason?: string; displayReason?: { readonly en: string; readonly [locale: string]: string } }

The comment above that type contains one key sentence:

TEXT
Input rewriting is excluded because arguments are already logged and presented.

DSH does not allow arguments to be rewritten before execution, and that single fact decides dsh-hitl's "modify" semantics (chapter 7).

The mapping:

What the person did Settlement source Becomes
approve user { kind: 'allow' }
【Modify】 after editing text user { kind: 'deny', reason: the revision note } (default)
reject user { kind: 'deny', reason: the rejection note + the user's words }
countdown reaches zero, action=approve timeout { kind: 'allow' }
countdown reaches zero, action=reject/notify timeout { kind: 'deny', reason: the timeout note }
request withdrawn abort / host { kind: 'cancel' }

The code:

JavaScript
// index.js
function toPreToolDecision(exec, request, mount, settlement) {
  if (settlement.decision.kind === 'approve') return { kind: 'allow' }
  if (settlement.decision.kind === 'cancel') return { kind: 'cancel' }
  const revising = isRevision(settlement.decision)
  if (revising && mount.options.modify.mode === 'allow-and-inform' && settlement.source === OUTCOMES.user) {
    revisions.set(exec, { request, decision: settlement.decision })
    return { kind: 'allow' }
  }
  const info = settlement.source === OUTCOMES.timeout
    ? FAILURES.timeout
    : (revising ? FAILURES.revised : FAILURES.rejected)
  return {
    kind: 'deny',
    reason: capReason(describeDecision(request, settlement.decision, settlement.source)),
    info,
  }
}

cancel differs from deny in this: deny is a tool result saying "a policy refused", carrying reason and info; cancel is DSH's canonical cancellation result, meaning the turn was interrupted. A withdrawal is not a rejection and should not look to the model like somebody said no.

deny travels through the tool pipeline and ends up as:

"Cannot be reached" is not guessed from session state; the panel runs a hit test on itself once a second:

  ...
  const rect = element.getBoundingClientRect()
  if (rect.width <= 0 || rect.height <= 0) return true

  ...
}

a modify decision must carry at least one field change

The host sends a ping every 15 seconds; if the browser half receives no frame for 45 seconds it rebuilds the connection. It needs this because a plugin reload or a laptop going to sleep can leave a socket open that delivers nothing, and EventSource will not notice on its own.

6.4 Subagent pass-through: one request, two filings

Every tool call inside an in-process subagent (spawn / fork) goes through the same gate, because the tool pipeline is the same one.

A problem appears immediately: that call happens inside a child session, and pending decisions belong to a session — a panel takes over a composer only for the session you are looking at. If you are looking at the main session, the subagent's request lands on no panel at all.

The plugin therefore files every request twice:

Filing What it buys
the session that made the call open that subagent's session and the panel is there
the session you are looking at now whichever session you are in, the panel appears in the composer in front of you

In code it is one request plus a view copy:

JavaScript
export function filingSessions(request, viewSessionId) {
  const own = request?.sessionId
  if (typeof own !== 'string' || own === '') return []
  if (typeof viewSessionId !== 'string' || viewSessionId === '' || viewSessionId === own) return [own]
  return [own, viewSessionId]
}

The copy is not a second owner; it forwards decisions to the original request:

JavaScript
class PendingHitlView {
  constructor(primary, sessionId) {
    this.kind = KIND
    this.key = `${primary.key}@view`
    this.sessionId = sessionId
    this.primary = primary
  }
  get request() { return this.primary.request }
  get sequence() { return this.primary.sequence }
  get answerable() { return this.primary.answerable }
  answer(decision) { return this.primary.answer(decision) }
  ...
}

Both filings point at the same request, so deciding in either place settles the same call, first answer wins. Switch sessions and the follow-along filing moves with you, because the client subscribes to the binding source for "the session currently shown":

JavaScript
const readView = () => {
  const source = ctx.uiSession?.adapter?.current
  const binding = source === undefined || source === null ? undefined : source.value
  const id = binding === undefined || binding === null ? undefined : binding.key

Why this is necessary is in the comment: the status dot on a DSH sidebar row only knows the built-in kinds approval / plan-review / question, and this plugin's kind: 'hitl' is not among them, so the child session's row shows no dot at all. Without the follow-along filing, a subagent's gated call would silently wait for its countdown to end.

Does it trigger? It depends on the subagent backend:

Subagent backend Triggered Why
spawn / fork (in process) yes the child is another agent in the same process, and the tool pipeline is the same one
dsh-sdk / acp / claude-code / codex (out of process) no their tool calls happen in another process and never pass tools/pre-execute

Once it triggers, the subagent's call stops at the gate (its turn stalls), the parent's subagent call is waiting on the child, and the whole turn stops with it. What you see on screen may be nothing more than "the subagent is still running".

One practical rule follows: give any mount a subagent might call a countdown. Without one it waits forever, and nobody is there to click for the child.

6.5 The countdown is always the host's number

A countdown has one easily-hit failure mode. A card's request object is built once, when the card appears, and the remainingMs it carries is the full length of the countdown, not "how much is left right now". And that object gets sent out repeatedly:

TEXT
the request frame for a new request
the snapshot frame on reconnect
the ack frame for a hold

Resend it verbatim and a browser that receives it late (a refreshed page, a reconnected stream, a hot-reloaded client half) adds the elapsed time back on, so the panel "claims" time this call no longer has.

So no frame may carry that original object; each must carry what the host computes at that moment. The host does it with one projection function:

JavaScript
function liveRequest(request) {
  if (request.countdown === null || request.countdown === undefined) return request
  const remainingMs = registry.remaining(request.id)
  if (remainingMs === null) return request
  return { ...request, countdown: { ...request.countdown, remainingMs, held: registry.held(request.id) } }
}

It is used in all three places above, so every frame that goes out describes "right now".

The browser half then treats it as a reading, not as "start counting again from now":

JavaScript
export function deadlineOf(reading, now) {
  const remainingMs = reading?.countdown?.remainingMs
  if (typeof remainingMs !== 'number') return undefined
  const observedAt = typeof reading.observedAt === 'number' ? reading.observedAt : now
  return observedAt + remainingMs
}

The reading means "this much was left at the moment it arrived". Anchoring it to the arrival time buys three things: remounting, receiving the frame twice, and re-rendering all leave the deadline where it was. One further benefit is easy to miss — it trusts only a duration, never a timestamp, so it is immune to clock skew between host and browser.

The number on screen is assembled from three inputs:

JavaScript
export function reconcileClock({ id, at, frozen, hostHeld, now }) {
  let deadlineAt = at
  let hold = frozen
  if (hostHeld) {
    if (hold === undefined || hold.id !== id) {
      hold = { id, remainingMs: deadlineAt === undefined ? 0 : Math.max(0, deadlineAt - now) }
    }
  } else if (hold !== undefined && hold.id === id) {
    if (deadlineAt !== undefined) deadlineAt = now + hold.remainingMs
    hold = undefined
  }
  const remaining = hold !== undefined
    ? hold.remainingMs
    : (deadlineAt === undefined ? undefined : deadlineAt - now)
  return { at: deadlineAt, frozen: hold, remaining }
}

The comment records that each of the three rules fixed a real defect:

TEXT
1. Capture the remainder once when a pause starts; during the pause the number does not move,
    otherwise a panel that says "paused" keeps counting down on its own.

2. On resume, re-base the deadline in the same place,
   otherwise the frame that resumes paints the original deadline that has already expired.

3. With no pause, derive the remainder from the deadline on every render —
   which is exactly why a countdown can jump.

The client only trusts the host's verdict on a pause:

JavaScript
setHold(id, held) {
  if ((state.holds?.[id] === true) === held) return
  state = { ...state, holds: { ...state.holds, [id]: held } }
  emit()
}

A local focus flag cannot claim a pause the host has not approved. A page refresh also reads countdown.held out of the snapshot, so a refresh cannot leave the panel pretending to still be paused.

7. What you press, what the agent receives

The earlier chapters mentioned parts of this; this chapter gives the full mapping in one place, including the one point most likely to surprise you: after you edit the text and press 【Modify】, the tool does not run by default.

What the user did Does the tool run? What the agent receives
【Approve】 yes the tool's normal result
【Modify】 after editing text (default revise-request) no HITL: the user revised the proposal, so tool "x" did not run. Re-issue the call with these changes: + - param: new text for every changed field
【Modify】 after editing text (allow-and-inform) yes the tool's normal result + one user message right after it carrying the edited text
【Reject】 no HITL: the user rejected tool "x" and it did not run.; with the feedback box filled in, … User feedback: <verbatim>

Why does 【Modify】 not run the tool by default?

The reason is on DSH's side: arguments cannot be rewritten before execution. PreToolDecision has exactly allow / deny / cancel / ask, and "rewrite the arguments" is still a proposed design.

So dsh-hitl's "modify" hands the edited content back to the agent, which re-issues the call with the new arguments. That is the most honest semantics — the tool genuinely did not run with the old arguments — and the log stays consistent: a session record never shows "the arguments were A but B ran".

If your tool can genuinely accept "run now, be told about the edit afterwards" (a recorder or a display, say), set modify.mode to allow-and-inform.

Implementing that branch also fixed a leak:

because a plain-JS plugin cannot import the host's createUserMessage factory.

8. The security boundary

This chapter answers two questions: what happens when nobody can be reached, and what this gate can actually hold.

8.1 The channel's three checks

The decision channel answers only loopback addresses, and compares tokens in constant time:

JavaScript
function authorized(req, queryToken) {
  const header = req.headers.authorization
  const bearer = typeof header === 'string' && header.startsWith('Bearer ') ? header.slice(7) : undefined
  const presented = typeof queryToken === 'string' && queryToken !== '' ? queryToken : bearer
  if (typeof presented !== 'string' || presented === '') return false
  const candidate = Buffer.from(presented)
  let accepted = false
  for (const known of tokens) {
    const expected = Buffer.from(known)
    // Every candidate is compared, so timing does not reveal which token matched.
    if (candidate.length === expected.length && timingSafeEqual(candidate, expected)) accepted = true
  }
  return accepted
}

There is no early break in that loop: every candidate is compared, so "how many were tried before the match" cannot leak through timing.

The POST side has two more:

JavaScript
if (!loopback(req) || !authorized(req, url.searchParams.get('token')) || !sameOrigin(req)) { ... }
if (typeof contentType !== 'string' || !contentType.includes('application/json')) { ... }

Plus the body limit maxBodyBytes: 256 * 1024.

These checks stop other web pages on the same machine (CSRF / DNS rebinding), not local processes — a local process can read ~/.dsh anyway.

The token itself has one design point: it is issued once per process.

JavaScript
function processTokens() {
  const existing = globalThis[TOKEN_REGISTRY]
  if (existing instanceof Set) return existing
  const registry = new Set()
  Object.defineProperty(globalThis, TOKEN_REGISTRY, { value: registry, enumerable: false })
  return registry
}

The token is injected into every page that is served. If a plugin reload minted a new token, every open page would hold the old one, its event stream could never open again, and the only way out would be a manual refresh. So one token is minted on first activation and reused by every later activation, and every token this process has issued stays accepted until the cap pushes it out. The cap is 8 (TOKEN_MEMORY), oldest first.

8.2 With no browser: reject by default

whenUnavailable decides what happens unattended, and the default is reject: with no browser connected, a gated tool is rejected.

If nobody can be asked, nothing is let through. That default carries a second meaning that does not depend on whether a UI exists: in a composition with no web service at all (headless / TUI) the plugin stays active and keeps gating. "No UI, therefore no gate" is not this plugin's semantics.

The /status route is a deliberate exception:

JavaScript
if (url.pathname === `${endpoint}/status`) {
  // Read-only troubleshooting surface: no token, no payload, loopback only.
  if (req.method !== 'GET' || !loopback(req)) { ... }
  sendJson(res, 200, {
    ok: true,
    clients: clients.size,
    tokens: tokens.size,
    protecting: service.list(),
    pending: service.pending().map(request => ({ ...request,
      remainingMs: registry.remaining(request.id), held: registry.held(request.id) })),
  })
  return
}

It contains only the connected browser count, the tokens this process has issued, the mounted tools, and the pending list (tool name / session id / remaining milliseconds / hold state). No token, and no tool arguments at all.

The size of that exposure is spelled out in the comment: a process on the same machine can already read the session logs under ~/.dsh/sessions/**, which hold every tool argument, so /status exposes a strictly smaller subset of what is already readable locally.

8.3 What it stops, and what it cannot

The gate is installed at one position only — before the call begins — so it governs "whether to begin", not "what happens once begun".

One limit has to be accepted: if a tool has already produced a side effect inside its own execution layer (a concurrency race, an asynchronous write, a request already sent), a rejection stops only what comes next. It cannot roll back what already happened.

HITL is therefore neither a transaction nor a sandbox.

How safe you actually are depends on two things: how dangerous the operations your matcher covers are, and whether the tool puts its irreversible step last. Mounting bash / write / edit — dangerous the moment they start — is the right use. If a tool's risk only appears halfway through, HITL can only help you decide whether to begin.

8.4 How it relates to the rest of DSH

dsh-hitl stands at the front of the pipeline, but others stand behind it.

Ask the human first, screen afterwards. The plugin uses tools/pre-execute with prepend: true; once the user agrees, the sandbox, guards, hooks, approval, and other policies take effect afterwards as usual. You can see this directly in the host code — after the waterfall returns allow, there is still a guard check:

TypeScript
const denialReason = decision.kind === 'allow' ? this.guardReason(exec) : decision.reason

Hence a phenomenon that looks contradictory and is by design: the user agreed, and the tool is still refused by the sandbox or a guard. The reverse holds too — another pre-execution policy may refuse before this plugin is ever reached, in which case no HITL panel appears at all. So both "it ran without showing me a panel" and "it failed without showing me a panel" should send you to the other policies first.

Approval asks "may this happen"; HITL asks "may it happen this way". DSH ships an approval seam (ctx.approval) that is a different thing from dsh-hitl:

TypeScript
// docs/subsystems/approval.md
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'

allowed-once authorizes only the one action that was asked about; callers refuse on rejected / cancelled / unavailable alike. Its request deliberately carries no arguments:

an answerer attaches the prompt to the already-streamed tool call through callId
instead of rendering a second copy that could drift.

10.1 No card appeared

Check three things, in the order the mounting layer resolves them.

First the matcher. The cheapest check is ctx.hitl.list() or the protecting field of /status, to confirm the mount exists at all. If it does, check that the matcher can really hit — glob strings and regexes are both easy to get slightly wrong, e.g. mcp__* only matches names that begin with mcp__.

Second enabled. It is a boolean or an (exec) => boolean; returning false for this call means no gate was installed this time.

Third the log. A config error does not stop the plugin from loading; it leaves one warning prefixed dsh-hitl:, which is easy to scroll past.

If all three are fine, the problem may be another pre-execution policy: some earlier hook already refused this turn, so the panel never had a chance.

10.2 The card appeared, but approving still failed

That is usually correct behaviour. HITL is first in the pipeline; after the user approves, the sandbox, guards, and hooks still apply. Approval clears "whether to run", not the gates behind it. Read the error code in the tool result: if it starts with HITL_, this plugin refused; otherwise go to the subsystem named.

10.3 Still gated after unloading the plugin

protect() was called without owner. The mount is recorded in hitl's closure, and the caller's fiber unloading does not touch it. Clear it for now with ctx.hitl.unprotect('tool'); for a real fix see §4.4.

10.4 A subagent hangs

The symptom is "the subagent is still running" on screen with no card anywhere. First check whether the subagent backend is the in-process spawn / fork — out-of-process backends never pass tools/pre-execute and do not trigger. If it is in-process, its call is sitting at the gate waiting for a decision while you are not looking at that session. Give such mounts a countdown and let the timeout policy cover it.

10.5 The countdown looks wrong

Separate "the number jumps" from "the number never decreases". Jumping is usually a re-base on render (§6.5, third rule); never decreasing means the hold was never released — check whether the host-side hold graceTimer has fired (5 minutes by default).

Appendix A: the machinery behind owner

This appendix explains the mechanism behind the rule in §4.4: why owner can release a mount automatically, and why one form that looks equivalent silently fails. If you only want to use it, §4.4 is enough.

A.1 The lifetime contract of an effect

"Pass owner and it unbinds itself" works because of one hard contract in Cordis about effect:

TEXT
`execute` runs immediately; the disposers it produces are collected and run
(in reverse order) either when the returned disposer is called or
when the fiber unloads, whichever comes first.

Unpacked, that is three steps:

TEXT
1. the effect body runs immediately and the disposers it produces are collected
2. two triggers: the returned disposer is called, or this fiber unloads
3. whichever comes first wins

So owner.effect(() => release, label) means: file this release against the owner's fiber. When the owner plugin is unloaded, disabled, reloaded, or restarted by a config change, the fiber unloads, its effects run in reverse order, release() executes, and this mount is spliced out of hitl's mounts array.

A.2 Why a cleanup function returned from apply is never called

Both forms "return a function", and one is collected while the other is dropped:

Form Result
function apply(ctx) { return release } dropped
ctx.effect(() => release, label) collected

The reason is that Cordis's "class branch" only recognises one initialisation protocol. Both paths, in full:

TypeScript
// vendor/cordis/src/fiber.ts
execute: function () {
  if (isConstructor(runtime.callback)) {
    const instance = new runtime.callback(this.ctx, this.config)
    for (const hook of instance?.[symbols.initHooks] ?? []) {
      hook()
    }
    return instance?.[symbols.init]?.()                            // ← only the protocol method's return value
  } else {
    return runtime.callback(this.ctx, this.config)                 // ← the return value is the ledger entry
  }
},

isConstructor does one thing:

TypeScript
export function isConstructor(func: any): func is new (...args: any) => any {
  // async function or arrow function
  if (!func.prototype) return false
  if (func instanceof GeneratorFunction) return false
  ...
  return true
}
TEXT
a synchronous function has a prototype  → true  → takes the "class branch"
arrow / async functions have none       → false → ordinary call
generator / async generator             → false → ordinary call

Here is the part that is very easy to get wrong: new does not discard the returned function. The rule for new is "if the return value is an object, use it; otherwise use the fresh instance", and a function is an object:

JavaScript
function nothing() {}
new nothing()                  // {}          — no return value, so the fresh instance

function primitive() { return 42 }
new primitive()                // {}          — a primitive return value, so the fresh instance

function apply() { return () => {} }
typeof new apply()             // 'function'  — an object was returned (a function is an object), so it is used

So instance really is the disposer you returned. The problem is the next line: the class branch believes instance is a Service instance, so it reads instance[initHooks] and instance[init] — the protocol methods a Service subclass uses to declare what it registered. A plain disposer function has neither, so instance?.[symbols.init]?.() short-circuits to undefined, execute returns undefined, and nothing reaches the ledger.

The measured ledger (reading fiber._disposables directly):

TEXT
A  function apply(ctx) { return d }     isConstructor = true
   ledger: [(effect wrapper)]                     ← d is not in it

B  const apply = ctx => d               isConstructor = false
   ledger: [(effect wrapper), d]                  ← d is in it

   what the class branch got from new apply(ctx):
     typeof = function, tag = "returned-from-apply"   ← new did return it
   but what it reads:
     initHooks = undefined, init = undefined           ← so it cannot see the entry

That is also why the arrow-function path works:

TEXT
new applyArrow(...)  →  TypeError: applyArrow is not a constructor

It simply cannot be new-ed, which is exactly why isConstructor returns false, so it takes the ordinary call and the return value is collected.

The full matrix:

Form of apply isConstructor Return value collected?
function apply(ctx) { return d } true no
async function apply(ctx) { return d } false yes
function* apply(ctx) { yield d } false yes
const apply = ctx => d false yes
a Service subclass true via the [Service.init] protocol

Only the synchronous function declaration trips over this, and it is precisely the form DSH plugins use most:

JavaScript
export function apply(ctx, config = {}) { ... }

A Service subclass uses the other protocol and is unaffected:

TypeScript
// as written in DSH
async* [Service.init](): AsyncGenerator<() => Promise<void>, void, unknown> {
  ...
}

Every disposer it yields is collected. And ctx.effect takes the collecting path, which explicitly collects a returned function:

TypeScript
// vendor/cordis/src/fiber.ts — _execute()
const effect: Effect = runner.execute.call(this)
if (typeof effect === 'function') {
  return runner.collect(effect)      // ← collected here
}

Measured across four forms, unloading each caller plugin in turn (using the vendored Cordis in this repository):

TEXT
1: owner = the caller's ctx           → unload → "bash" released ✓
2: no owner, returned from apply      → unload → "write" STILL MOUNTED ✗
3: the caller wraps it in ctx.effect  → unload → "edit" released ✓
4: owner = the ctx from ctx.inject    → unload → "glob" released ✓

Row 2 is exactly the symptom at the start of §4.4: the plugin row is unloaded and the mount is still in effect, so the tool keeps being intercepted.

Appendix B: why it runs its own channel

You do not need this to use the plugin. It explains the constraint behind "the plugin opens its own HTTP channel" in §3.2, and how that constraint decided almost every implementation detail downstream.

B.1 Neither existing channel is available

DSH has two ready-made host-to-browser channels, and both of their seats are assigned at build time.

Channel one: the Remote namespace (Typert).

For a package to let the browser call its host methods, it has to go through a whole generation chain:

TEXT
annotate methods with @Remote inside the package, bind a wire namespace
  → at build time dsh-typert-generator analyses the public types
  → produces a /remote artifact (an executable schema factory plus declarations)
  → the client assembly explicitly imports those artifacts
  → ctx.remote.$mount(contribution) mounts it

Every step happens at build time, not at run time:

TEXT
Generator: Generation runs only at build time and never in a live agent session.
Assembly manifest: The capability set is fixed by explicit build-time value imports;
         the Client does not discover the Host's active Services or
         Remote definitions at runtime.
          Additional capabilities require an explicit `/remote` value import
          and mount in this assembly.

That "assembly manifest" is a list of explicit imports inside the shipped shell:

TypeScript
// packages/api/remotes/src/client/index.ts
import userQuestionsRemote from '@deepseek-ai/dsh-user-questions/remote'
import commandsRemote from '@deepseek-ai/dsh-commands/remote'
import goalsRemote from '@deepseek-ai/dsh-goal/remote'
// … one line each, all written at build time

Channel two: the forwarded-event allowlist.

Host events reach the browser through an allowlist hard-coded in the source:

TypeScript
// packages/api/remotes/src/remote-events.ts
/**
 * The one home of this application's forwarded-Host-event allowlist.
 * …the legal key set of `ctx.remote.$on`.
 */
export const API_REMOTE_FORWARDED_EVENTS = [
  { event: 'agent-preset/selected', mode: 'emit' },
  { event: 'approval/request', mode: 'waterfall' },
  …
  { event: 'user-questions/request', mode: 'waterfall' },
] as const satisfies readonly TypertForwardableEventEntry[]

That declaration is three things at once: the host-side forwarding loop, the legal set of event keys on the client ($on<Event extends TypertRemoteEvent>), and a TypeScript type surface. Without it TypertRemoteEvent is never in the compiled surface, so every $on call fails to compile.

The allowlist already seats DSH's own two HITL panels:

TEXT
approval/request          ← DSH's built-in approval panel
user-questions/request    ← DSH's built-in question panel

approval and question sit at that table, and there is no third chair. The cost of adding one is written down in the docs:

TEXT
Forwarding one more event requires one entry in that array:
the type projection, consumer key face, and Host forwarding loop all derive from it.

B.2 A package installed through a profile can use neither

What dsh plugin add does is put a package into the profile's node_modules and add one loader row.

TEXT
no repository build   → nothing generates the /remote artifact
no compile step       → nothing adds an import line to the assembly manifest
no source             → nothing adds an entry to the as const array

So one path is left: cut your own hole in the wall, then fit your own lock.

Strictly, the limit is not physical but build-time: there is no seat reserved for dsh-hitl at that position. The client module table has an external field that lets an entry declare the non-baseline modules it needs, and a client plugin could in principle $mount a pre-generated contribution itself. But that would require the plugin author to run the generator at release time and ship the artifacts alongside.

B.3 What follows from that constraint

Choosing to run its own line decided almost every implementation detail afterwards:

TEXT
because the line is its own   → it needs its own token, its own handshake, its own reconnect
because the line is its own   → it has to judge "is the page still there" itself (heartbeat and watchdog)
because the line is narrow    → the proposal must be computed host-side, and the front end only renders

The third line is the computed fields of §5.4: content is worked out host-side and then pushed to the browser, which only renders it. That is why the browser half never needs to read a disk or reach an external service, and why what it can know is limited to what the host chooses to hand over.
